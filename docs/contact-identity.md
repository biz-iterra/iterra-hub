# 連絡先の同一性と名刺（異動・転職への対応）

名刺は「その人の、ある所属における連絡手段」である。人は変わらないが所属は変わる、
という前提でモデルを組む。

対象は `contacts`（連絡先）と、名刺 CSV 取込（`docs/lead-import-eight.md`）の判定部分。

## 1. 出発点：日付は当てにならない

Eight の CSV には「名刺交換日」という列があるが、**実態は利用者が Eight にデータを
登録した日**であり、名刺を受け取った日でも、その人がその会社に在籍していた期間でもない。

この日付を所属の時系列の根拠にすると、次の事故が起きる。

> 2020 年にもらった前職の名刺を、今日まとめて Eight に登録する。
> 登録日が最新になるため、**前職が現在の所属として採用され、現職を上書きする。**

したがって **日付を所属の順序の根拠にしない。** 代わりに使えるのは、
名刺そのものに書かれた連絡手段である。

- **メールアドレスは会社ドメインを含む**ため、所属の裏付けそのものになる
- **携帯番号は転職しても変わらない**ため、人の同一性の手掛かりになる

## 2. 現状の問題（対応前）

`contacts` は所属を単一の値で持つ（`company_id` / `department` / `job_title`）。

| 場面 | 対応前の挙動 | 問題 |
|---|---|---|
| 転職後の名刺を取り込む | 「会社 × 姓名一致」が外れて別人として新規作成 | 同一人物が二重に存在する |
| 異動後の名刺を取り込む | 部署・役職は空欄補完のみ | 旧部署のまま残る |
| 旧所属の情報 | 保持されない | どの会社の名刺だったかが失われる |

## 3. 決定事項

| 論点 | 決定 |
|---|---|
| 名刺の持ち方 | **`business_cards` を新設し、メール・電話の行へ FK で紐づける** |
| 現在の所属 | **自動では切り替えない。人が名刺を選んで反映する** |
| 姓名一致のみ（メール・電話が一致しない） | 別人として取り込み、統合候補として画面に出す |
| 転職を検知したときの旧リード | そのまま残す。新しい名刺は別リードになる |

誤統合も誤った上書きも元に戻すのが難しいため、**判断できないものは人に見せる**方針で一貫させる。

## 4. データモデル

### 4.1 `business_cards`（新設 / D11）

名刺 1 枚を 1 行として持つ。

| カラム | 型 | 説明 |
|---|---|---|
| `contact_id` | UUID NOT NULL | → `contacts` ON DELETE CASCADE |
| `contact_email_id` | UUID | → `contact_emails`。**この名刺のメール** |
| `contact_phone_id` | UUID | → `contact_phones`。**この名刺の電話** |
| `company_id` | UUID | → `companies`。特定できない名刺は NULL |
| `company_name_raw` | TEXT | 名刺に書かれていた会社名 |
| `department` / `job_title` | TEXT | |
| `address_id` | UUID | → `addresses` |
| `source` | TEXT | `eight` / `manual` / `import` |
| `source_external_key` | TEXT | 取込元での一意キー。再取込で名刺を増やさない |
| `source_registered_on` | DATE | **取込元にデータを登録した日。在籍期間ではない** |
| `is_primary` | BOOLEAN | 現在の所属として採用している名刺。`contact_id` ごとに 1 枚 |

制約: 会社 ID と会社名のどちらも無い行は作れない / `(source, source_external_key)` は一意 /
`is_current` 相当の `is_primary` は 1 人 1 枚（部分 UNIQUE インデックス）。

**カラム名を `source_registered_on` にしているのは誤用を防ぐため。**
`exchanged_on` や `started_on` という名前だと、在籍期間として使われてしまう。

### 4.2 `contacts` の所属カラムの位置づけ

`company_id` / `department` / `job_title` は**現在の所属**であり、
**人が決めた値**である。取込では書き換えない。

書き換えるのは `apply_business_card_as_current()` だけで、これは画面の
「現在の所属にする」からしか呼ばれない。

### 4.3 `contact_merge_candidates`（新設 / D12）

姓名のみ一致した組を記録する。`status` は `pending` / `merged` / `rejected`。
ペアの向きは UUID の大小で正規化し、`(A,B)` と `(B,A)` を別候補にしない。

### 4.4 `contacts.merged_into_contact_id`

統合で吸収された側に入る。物理削除はせず `deleted_at` と併せて閉じる。

## 5. 人物の同定

`resolve_or_create_contact` は上から順に判定し、決まった時点で下は見ない。

| 段 | 条件 | 判定 | 根拠 |
|---|---|---|---|
| P1 | `contact_emails` にメールが完全一致 | 同一人物 | 最も確実 |
| P2 | **携帯番号**が一致 かつ 姓が一致 | 同一人物 | 転職しても携帯は変わらない |
| P3 | 会社 × 姓 × 名 が一致 | 同一人物 | 従来の判定 |
| P4 | 姓 × 名 のみ一致 | **別人として作り、統合候補に記録** | 同姓同名の誤統合を避ける |

**P2 は携帯に限る。** 代表電話で判定すると同じ会社の全員が一致してしまうため、
`is_mobile_phone()`（`070`/`080`/`090` + 8 桁）で絞る。照合は数字だけに正規化するので
ハイフンの有無は問わない。

種別の判定は `phone_line_type()` にまとめてある。**日本の番号計画では市内局番の先頭が
2〜9**（0 と 1 は特番・事業者識別に予約）なので、3 桁目が 0 になるのは市外局番が
`0X0` 形式のものだけであり、固定電話と確実に区別できる。

| 種別 | 番号 | 同定キー |
|---|---|---|
| `mobile` | 070 / 080 / 090 | **使う** |
| `ip` | 050 | 使わない（**会社の代表番号としても使われ、社内で共有されうる**） |
| `other_non_landline` | 020 / 060 | 使わない |
| `toll_free` | 0120 / 0800 / 0570 | 使わない（会社の窓口で個人に紐づかない） |
| `landline` | 上記以外の 0 始まり | 使わない |
| `unknown` | 海外番号など | 使わない |

ラベル（`contact_phones.label`）は `default_phone_label()` が決める。
IP 電話を `work`（会社の固定電話）として記録しないための区別。

**P4 でカナを見る。** カナが両方あって食い違えば候補にも挙げない。

## 6. 名刺の記録と所属の切り替え

### 6.1 取込時（`record_business_card`）

1. メール・電話の行を引き、その ID を名刺に持たせる
2. `source_external_key` で既存の名刺を探し、あれば内容を更新（再取込で増やさない）
3. **連絡先の現在の所属は書き換えない**

例外は「連絡先の現在の所属が、この名刺と同じ会社のとき」。その名刺が現在の所属を
表しているので採用済みの印だけ付ける（値は同じなので上書きは起きない）。

### 6.2 人が切り替えるとき（`apply_business_card_as_current`）

画面の「現在の所属にする」から呼ぶ。名刺の会社・部署・役職を `contacts` に写し、
`is_primary` を付け替える。**これ以外に `contacts` の所属を書き換える経路は無い。**

## 7. 値の優先ルール

| 項目 | 規則 |
|---|---|
| 会社・部署・役職 | 取込では**書き換えない**。名刺として別に残す |
| メール・電話 | **追加**。旧アドレスも残す（過去のやり取りの参照先を壊さないため） |
| その他 | 空欄補完のみ |

## 8. 取込フローへの反映

ドライランで出すもの:

| 区分 | 意味 |
|---|---|
| 新規 / 更新 | 外部キーが既存リードと一致するか |
| **同姓同名あり** | 姓名が一致する連絡先が既にある。**別人として取り込まれる**旨と、名刺側・既存側の所属先を併記 |
| スキップ | エラー行 |

取込結果で出すもの:

| 区分 | 由来 |
|---|---|
| 名刺の枚数 | `record_business_card` が記録した数 |
| 統合候補 | `detect_contact_merge_candidates` が記録した組の数 |

結果には「連絡先の現在の所属は変更していない」ことを明記する。

## 9. 統合（マージ）

`merge_contacts(p_keep, p_merge)` を DB 関数として実装する。複数テーブルへの
書き込みなので単一トランザクションにする。

付け替え対象:

| テーブル | 備考 |
|---|---|
| `contact_emails` / `contact_phones` | 一意制約の衝突は読み飛ばして捨てる |
| `business_cards` | すべて移す。**採用済みの印は残す側を優先**（所属を勝手に変えない） |
| `account_contacts` / `email_message_contacts` | 衝突は読み飛ばす |
| `leads` / `deals` / `contracts` | 付け替え（`promoted_contact_id` / `counterparty_*` も） |
| `talents` | **1:1 制約。** 両方にあれば例外を投げて手動判断に回す |
| `financial_info` / `other_addresses` / `companies.primary_contact_id` | 付け替え |
| `activity_logs` / `deal_activities` / `contact_change_histories` | 履歴なので付け替えて残す |

統合された側は `deleted_at` + `merged_into_contact_id`。物理削除しない。
**取り消せない前提**で、`merge_contacts_preview()` の件数を確認ダイアログに出してから実行する。
権限は manager 以上（DB 関数側でも確認）。

## 11. 未決事項

- **兼務・複業**: 現在の所属を 1 つに限定している。名刺は複数持てるので、
  兼務を扱うなら `is_primary` の一意制約を外す
- **改姓**: 姓が変わると P1（メール）か P2（携帯）でしか同定できない
- **会社の統廃合**: `companies` の統合は別テーマ
- **退職済みメールの扱い**: 使えなくなったアドレスに印を付ける仕組みは無い。
  名刺は残るので、どの会社の連絡先だったかは追える
