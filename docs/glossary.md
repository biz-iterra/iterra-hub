# ITERRA CRM 用語集

本ドキュメントは `iterra-hub`（ITERRA CRM）プロジェクトで使用する用語の定義を統一するための参照資料。
会話・設計書・コード・コミットメッセージでの用語の揺れを防ぐため、ここに記載された表記・意味を正とする。

- 論理名（日本語）と物理名（DB テーブル名・カラム名）は原則として 1:1 で対応する。
- 類義語（「企業／法人／会社」など揺れやすい語）は **採用語** と **非採用語** を明記する。揺れが起きた場合は本ドキュメントに従って統一する。
- 新しい概念を追加する場合は、まず本ドキュメントを更新してからコード・設計書に反映する。

## 1. コアエンティティ

業務の中心となる 6 エンティティ。詳細は `docs/database-design.md` を参照。

| 論理名（採用） | 物理名 | 定義 | 非採用語 |
|---|---|---|---|
| **カンパニー** | `companies` | 組織の法的・登記情報を保持するエンティティ。法人番号・インボイス登録番号などを管理する。 | 企業、法人、会社、Corporation |
| **アカウント** | `accounts` | 取引主体。法人アカウント（カンパニー紐づき）と個人アカウント（コンタクト直接）の 2 種類がある。ディールは必ずアカウントに紐づく。 | 顧客、クライアント、取引先 |
| **コンタクト** | `contacts` | 個人。法人所属（corporate_rep / employee）または個人（individual）のいずれか。`contact_type` で判別する。 | 人、担当者（※文脈次第、後述）、連絡先、Person |
| **ディール** | `deals` | 取引。パイプライン → ステージ → ステータスの 3 階層で進捗管理する。アカウントへの紐づけが必須。 | 案件、ディール、取引（業務会話上の許容のみ） |
| **契約** | `contracts` | 契約情報。紙面／電子／口頭の契約方式を区別する。manager / admin のみ操作可能。 | Contract（英語表記は非推奨） |
| **タレント** | `talents` | コンタクトに 1:1 で紐づく人材特性情報。スキル・経歴・占い分析を持つ。 | 人材（※文脈次第）、候補者 |
| **プロジェクト** | `projects` | 複数ディールをグルーピングする業務イニシアチブ。1 プロジェクト : N ディール（中間テーブル `deal_projects`）。アカウントとは直接紐づかず、ディール経由で関連する。 | イニシアチブ、キャンペーン、施策 |

### 1.1 エンティティの関係性

```
カンパニー ─ 1:N ─ アカウント（法人）─ N:M ─ コンタクト（account_contacts 経由）
                                                ↑
カンパニー ─ 1:N ─ コンタクト（corporate_rep / employee は直接紐づき）
                                                ↓
                   アカウント（個人）─ N:M ─ コンタクト（individual のみ）
                                                ↓
                                              タレント（1:1）

ディール ─ N:1 ─ アカウント（必須）
ディール ─ N:M ─ プロジェクト（deal_projects 経由、任意）
プロジェクト ─ 1:N ─ プロジェクトメンバー（project_members、crm_users 参照）
```

> **重要な区別:**
> - 「カンパニー」は**法的実体**、「アカウント」は**取引の窓口**。1 つのカンパニーに複数アカウントが存在しうる（例: 本社アカウント・支店アカウント）。
> - コンタクトがカンパニーに直接紐づくのは `contact_type ∈ {corporate_rep, employee}` の場合のみ。`individual` の場合は `account_contacts` 経由でアカウントにのみ紐づく。
> - 「プロジェクト」はアカウントと直接リレーションを持たず、**ディール経由で間接的**に複数アカウントを束ねる。1 ディールは複数プロジェクトに属しうる（例: OEM 契約取引の共用）。

## 2. 「担当者」の定義（揺れやすい最重要語）

「担当者」は文脈によって指す対象が異なる。**単独で「担当者」と書くことは避け**、必ず修飾語を付ける。

| 採用語 | 意味 | 物理名の例 |
|---|---|---|
| **社内担当者** | ITERRA 社内でそのレコードを担当する CRM ユーザー。RLS のオーナー判定に使用。 | `owner_user_id` |
| **取引先担当者** | 取引先側の担当者コンタクト。カンパニーの代表窓口などに使う。 | `companies.primary_contact_id` |
| **代表者** | カンパニーの法的代表者（社長・代表取締役など）。名前のみ保持し、コンタクトとは紐づかない。 | `companies.representative_name` |
| **プロジェクト責任者** | プロジェクトのオーナー（1 名）。プロジェクトの方向性に最終責任を持つ。 | `projects.owner_user_id` |
| **プロジェクトメンバー** | プロジェクトに参加する CRM ユーザー。フラットなリスト（ロール区別なし）。ディール担当者の自動同期は行わず手動管理。 | `project_members.user_id` |

> **英語の対応:** `owner` = 社内担当者 / プロジェクト責任者。`primary_contact` = 取引先担当者。「所有者」という訳語は使わない。

## 3. ロール・アクセス制御

| 用語 | 値 | 権限範囲 |
|---|---|---|
| **member** | `member` | 自身が社内担当者（`owner_user_id = auth.uid()`）のレコードのみ閲覧・編集可能。 |
| **manager** | `manager` | 全件閲覧・編集可能。契約の CUD も可能。マスタ変更は不可。 |
| **admin** | `admin` | 全操作可能。マスタ CRUD・論理削除を含む。 |

| 用語 | 意味 |
|---|---|
| **多層防御** | Middleware（認証） + Server Action（認証・ロール・オーナー） + RLS（DB レベル）の 3 層でアクセス制御を行う方針。詳細は CLAUDE.md「アクセス制御ルール」参照。 |
| **オーナーチェック** | update 系 Server Action で `owner_user_id === user.id` を確認する処理（admin は除外）。RLS に依存せず Server Action 側でも実施する。 |
| **RLS** | Row Level Security。Supabase（PostgreSQL）の行単位アクセス制御機能。 |

## 4. ディール管理の階層

| 用語 | 物理名 | 定義 |
|---|---|---|
| **パイプライン種別** | `pipeline_types` | 取引の種類（営業／仕入れ 等）。ディール分類の最上位。 |
| **ディールステージ** | `deal_stages` | パイプライン内の進捗フェーズ。パイプライン種別に依存。 |
| **ディールステータス** | `deal_statuses` | ステージ内の状態。ステージに依存。 |

> 「ステージ」「ステータス」を単独で使うときも、必ず「ディール」の文脈であることを確認する。他エンティティ（`company_statuses`・`account_statuses`・`contact_statuses`・`project_statuses`）の「ステータス」と混同しない。

### 4.1 パイプラインとプロジェクトの直交関係

パイプラインとプロジェクトは**独立した軸**で、ディール 1 件が両方の軸を同時に持つ。

| 軸 | 役割 | 例 |
|---|---|---|
| **パイプライン種別** | 取引の「種類」 | 営業／仕入れ／外注 |
| **プロジェクト** | 取引の「目的／イニシアチブ」 | 万博プロジェクト／新店舗開業／OEM 契約 |

例: 万博プロジェクトは、A 社への**営業**ディール + B 社との**仕入れ**ディール + B 社との**仕入れ契約**ディールで構成されうる。

## 5. マスタの分類

| 分類 | 定義 | 例 |
|---|---|---|
| **静的マスタ** | 管理者のみ変更可能なコードマスタ。数十件程度。 | `lead_sources`, `account_types`, `skills`, `project_statuses` |
| **構造化マスタ** | 他マスタに依存する階層的マスタ。 | `deal_stages` (→ `pipeline_types`) |
| **参照マスタ** | 外部データソース由来の読み取り専用マスタ。件数固定。 | `number_diagnosis`（60 件）, `constellation_fortune_telling`（12 件） |

> **非採用語:** 「動的マスタ」は本プロジェクトでは使わない。admin が CRUD できるマスタでも、依存関係の有無で上記 3 分類のいずれかに割り当てる。

## 6. ポテンシャル診断

生年月日からタレントの性質を自動算出する機能。

| 用語 | 意味 |
|---|---|
| **ポテンシャルプロファイリング** | 動物占いベースの性質診断（全 60 パターン）。採用語は「ポテンシャルプロファイリング」。「動物占い」は内部実装の説明以外では使わない。 |
| **ポテンシャル番号** | 1〜60 の整数。`calcPotentialNumber(birthDate)` で算出。物理名 `potential_number`。 |
| **星座** | 誕生日から算出する 12 星座。`calcZodiacSign(birthDate)` で算出。物理名 `constellation`。 |
| **診断連携** | create / update 時に `applyBirthDateDiagnosis` で自動セットする処理。マスタ未投入時はエラーで中止する仕様。 |

| 値 | 採用語 | 紐づけ先 |
|---|---|---|
| `corporate_rep` | 法人代表コンタクト | カンパニー直接 |
| `employee` | 法人従業員コンタクト | カンパニー直接 |
| `individual` | 個人コンタクト | アカウント（`account_contacts` 経由） |

## 8. UI・UX 用語

| 用語 | 意味 |
|---|---|
| **カンバン** | ディール一覧のステージ別カード表示。列 = ステージ、カード = ディール。 |
| **テーブルビュー** | カンバンと切替可能な一覧表示形式。 |
| **ファネル** | ダッシュボードで使う、パイプライン進捗の漏斗状の可視化。 |
| **フォーカス** | 入力要素がキーボード入力を受け付ける状態。枠線色・focus ring が変化。採用色トークン: `--color-border-focus`, `--color-focus-ring`。 |
| **ホバー** | マウスオーバー状態。背景色は `--color-bg-hover` に統一。 |
| **focus ring** | フォーカス時に要素の周囲に表示される光彩効果（`box-shadow` で実装）。 |
| **エレベーション** | 影の強さ。`--elevation-low` / `--elevation-mid` などのトークン経由で使用。 |
| **遷移リンク** | 他画面へ遷移する UI。必ずアイコン（`ArrowUpRight` 等）を伴う。テキストのみのリンクは使わない。 |

## 9. 削除ポリシー

| 用語 | 意味 |
|---|---|
| **論理削除** | `is_active = false` で非表示にする削除方式。履歴・関連データは保持。本プロジェクトの**唯一の削除方式**。 |
| **物理削除** | DB から行を DELETE する方式。**本プロジェクトでは禁止**（監査証跡確保のため）。 |

> 現状 `deals` テーブルのみ `is_active` カラムが未導入のため、UI から削除操作を提供していない。

## 10. 変更履歴

| 用語 | 物理名の例 | 意味 |
|---|---|---|
| **変更履歴** | `*_change_histories` | エンティティのフィールド変更を記録する INSERT ONLY テーブル。UPDATE / DELETE 禁止。 |
| **ステージ遷移履歴** | `deal_stage_histories` | ディールステージの変更履歴。 |
| **アクティビティ** | `lead_activities` / `lead_customer_activities` / `deal_activities` / `email_messages` | 活動の記録の総称。画面では「社内対応」「顧客行動」「メール」の 3 つに分けて呼ぶ。横断一覧は `/activities`。 |
| **社内対応** | `lead_activities` | こちらから動いた記録（架電・名刺交換等）。 |
| **顧客行動** | `lead_customer_activities` | 相手が動いた記録（イベント参加・資料DL等）。 |

## 11. 技術用語

| 用語 | 意味 |
|---|---|
| **Server Action** | Next.js の Server Actions。書き込み処理（create / update / delete）は全て Server Action で実装する。 |
| **Server Component** | Next.js の Server Component。データ取得（read）に使用する。 |
| **Route Handler** | `src/app/api/` 配下の API エンドポイント。外部連携が必要な場合のみ使用。 |
| **Middleware** | `src/middleware.ts`。認証チェックとロール別ルーティングを行う。 |
| **トークン（デザイン）** | `src/styles/tokens.css` の CSS カスタムプロパティ。色・余白・角丸・影をトークン経由でのみ使用し、ハードコードは禁止。 |
| **トークン（認証）** | Supabase Auth の JWT。セッション管理に使用。文脈で区別する。 |

## 12. 非採用語リスト（参考）

以下の語は**使用しない**。相当する採用語を使うこと。

| 非採用語 | 採用語 |
|---|---|
| 企業／法人／会社 | カンパニー |
| 顧客／取引先／クライアント | アカウント |
| 担当者（単独） | 社内担当者 or 取引先担当者 |
| 所有者 | 社内担当者（owner） |
| 案件／ディール | ディール |
| 人材（エンティティ指すとき） | タレント |
| 動物占い（ユーザー向け文脈） | ポテンシャルプロファイリング |
| 削除（物理） | 論理削除（`is_active = false`） |
| 動的マスタ | 静的マスタ／構造化マスタ／参照マスタのいずれかに分類 |
| イニシアチブ／キャンペーン／施策 | プロジェクト |
