## 1. はじめに

### 1.1 何ができるシステムか

ITERRA CRM は「リードの獲得 → 育成 → ディール昇格 → 受注 → プロジェクト／契約管理」までを 1 画面で追う統合 CRM である。
従来の CRM に加え、**マーケティング（マーケティングオートメーション）** と **営業（セールスフォースオートメーション）** を同居させている。

- **マーケティング層**: リードの温度感・ステージ・コール履歴・キャンペーン紐付け。
- **営業層**: ディールのパイプライン進捗・プロジェクト・契約。
- **顧客情報層**: 連絡先・事業者情報・取引先・タレント情報。
- **ポテンシャル診断**: 生年月日から自動算出する性質分析（タレント／連絡先）。

### 1.2 本マニュアルの読み方

各機能の章は **「何ができるか」→「画面」→「作業フロー」→「注意点」** の順で構成している。
はじめて触る場合は第 2〜4 章 → 自分の業務に関連する章の順で読むと迷わない。

## 2. ログインとロール

### 2.1 ログイン

1. ブラウザで CRM の URL にアクセスする。
2. 未認証の場合、自動的に `/login` にリダイレクトされる（Middleware による制御）。
3. メールアドレスとパスワードを入力してログインする。
4. 認証成功後、ロールに応じた初期画面（ダッシュボード）に遷移する。

### 2.2 ロールごとにできること

| ロール | 参照範囲 | 主要な操作 | マスタ管理 | 契約操作 |
|---|---|---|---|---|
| **member** | 自分が社内担当者のレコードのみ | 連絡先/取引先/ディール等の CRUD（自分持分） | × | × |
| **manager** | 全件 | 全エンティティの CRUD、契約の CUD | × | ○ |
| **admin** | 全件 | 全操作（マスタ CRUD、論理削除、削除済みの復元） | ○ | ○ |

> 権限外の操作はボタン自体が表示されない／Server Action 側で拒否されるため、不正操作は発生しない。

### 3.2 ヘッダー

ログイン中ユーザー名・ロール、ログアウトボタンを表示。パンくずリストで現在位置を示す。
ユーザーメニューからは **「プロフィール設定」（`/profile`）** と「マニュアル」（`/manual`）へ移動できる。
Gmail 連携・Google コンタクト連携の接続はプロフィール設定で行う（§14.1 / §14.2）。

#### 横断検索（`Ctrl + K`）

ヘッダー中央の検索欄で、8 種類のデータを一度に探せる。
`Ctrl + K`（macOS は `⌘ + K`）でどの画面からでも検索欄にフォーカスが移り、
入力済みの語は全選択されるのでそのまま打ち直せる。

| 探せるもの | 検索対象の項目 |
|---|---|
| リード | リード名 / メールアドレス |
| ディール | ディール名 / **ディールコード** |
| 取引先 | 取引先名 / **取引先コード** |
| 事業者情報 | 事業者名 / **事業者コード** |
| 連絡先 | 姓 / 名 / **連絡先コード** |
| 契約 | 契約名 / 契約書名 / **契約コード** |
| プロジェクト | プロジェクト名 / **プロジェクトコード** |
| キャンペーン | キャンペーン名 |

- **コードでも引ける**（`CMP-` などの採番コード。リードとキャンペーンはコード列を持たないため名前・メールのみ）
- 候補の副題には**コード**が出る（同名のレコードが並んだときの見分けに使う）。
  リードだけはメールアドレス、キャンペーンはコードが無いため副題も出ない
- **2 文字以上**入力すると検索が始まる。入力が止まってから走るため、打っている途中では実行されない
- 種類ごとに最大 5 件。論理削除したものは出ない
- 見える範囲はロールに従う（member は自分の担当分のみ。§10）
- ↑ ↓ で候補を移動し Enter で開く。Esc または欄の外をクリックで閉じる

### 3.3 共通ボタンの意味

| ボタン | 意味 | 色 |
|---|---|---|
| 新規作成（`+ 新規登録`） | 新しいレコード作成ページへ遷移 | soleil（オレンジ） |
| 保存 | 編集内容を確定 | terra（濃紺） |
| キャンセル | 編集を破棄して詳細へ戻る | 透明 + terra 文字 |
| 削除 | 編集ページ内のモーダルで論理削除 | error（赤） |
| 外部リンク（`↗`） | 他画面へ遷移するテキストリンクには必ずアイコンが付く |  |

## 4. ダッシュボード

### 4.1 何が見られるか

`/dashboard` には 6 つの KPI カードと 4 つの可視化ブロックが並ぶ。

**KPI カード（上段）**

- 進行中ディール件数（`closed_at IS NULL`）
- 進行中ディールの合計金額（JPY）
- 今月クローズ件数（`closed_at` が当月）
- 取引先数（アクティブのみ）
- 連絡先数（アクティブのみ）
- 事業者情報数（アクティブのみ）

**可視化ブロック（下段 2×2 グリッド）**

- **パイプラインファネル**: ディールステージごとの進行中件数を横棒グラフで表示。
  **集計対象はセールスのパイプラインだけ**（2026-08-08）。プロキュアメント・パートナーシップは
  それぞれの画面で見る。
- **最近のディール**: 作成日時降順で上位 5 件。コード・名前・ステージ・金額・社内担当者。
- **最近のアクティビティ**: `activity_feed` の最新 5 件（社内対応・顧客行動・メールを横断）。種別・相手先・担当者・日時。「すべて見る」で `/activities` へ。
- **担当者別ディール数**: 進行中ディールの社内担当者別集計（件数降順）。

### 4.2 作業フロー

ダッシュボードは情報表示のみで編集操作はない。観察 → 詳細画面への遷移起点として使う。

1. 朝一でダッシュボードを開く。
2. パイプラインファネルで自分のディール分布を把握（要フィルタがないため、member は自分分のみ集計される）。
3. 最近のアクティビティで他メンバーの最新活動を確認。
4. 気になるディールがあればサイドバー「セールス」「プロキュアメント」「パートナーシップ」の
   いずれかへ移動し、ディール詳細へ遷移（一覧はパイプラインごとに分かれている。§6 前文）。

### 4.3 アクティビティ（`/activities`）

散らばっている活動の記録を 1 本の時系列にまとめた一覧。**閲覧専用**で、記録の追加・編集は
リードや連絡先の画面から行う。

**並ぶもの**

| 記録元 | 中身 | 追加する場所 |
|---|---|---|
| 社内対応 | 架電・名刺交換など、こちらから動いた記録 | リード詳細 → 社内対応 |
| 顧客行動 | イベント参加・資料ダウンロードなど、相手が動いた記録 | リード詳細 → 顧客行動 |
| メール | Gmail 連携で同期したやり取り | 自動（連携設定が前提） |

**絞り込み:** 記録元・担当者・期間（開始日／終了日）・キーワード（相手先／内容）。
1 ページ 30 件。

**見え方:** 自分が見られる範囲だけが並ぶ。member は自分が担当するリード・連絡先の分のみ、
manager / admin は全件（§10 と同じ規則）。

- 「結果」列は架電結果など、記録元が持っている場合だけ入る
- 時刻を入力していない記録は日付だけを表示する（`0:00` とは表示しない）
- 「相手先」からリード詳細・連絡先詳細へ移動できる

## 5. マーケティング（リード・キャンペーン）

### 5.1 リード（`/leads`）

#### 5.1.1 できること

- 見込み客情報を社名やフルネームで管理。
- ステージ × ステータス × 温度感 × デマンドファネル × 担当者で一覧を絞り込み。
- スコアによる並べ替え。
- **登録済みの事業者情報・連絡先に紐づけられる**（2026-08-08）。
- **ディール / オポチュニティステージへの遷移で、事業者情報・連絡先・ディールを自動生成**（Deal 昇格）。
  取引先（Account）は作られない（契約成立時に作られる）。

> **事業者情報 1 : リード N。** 同じ会社から 2 件目・3 件目のリードが来るのは普通のことなので、
> 事業者情報は 1 つに寄せる。登録済みなら作成画面の「事業者情報」欄で選び、未登録なら
> 「会社名」にテキストで書いておく（昇格時に事業者情報が作られる）。
> 事業者情報の詳細画面には、その事業者に紐づくリードの一覧と `+ リードを追加` が出る。

#### 5.1.2 画面構成

一覧ページ上部に以下のフィルタとアクションが並ぶ。

- 検索ボックス（氏名／社名／メール／電話の部分一致）
- ステージ・ステータス・デマンドファネル・温度感・担当者のドロップダウン
- スコアでソートボタン
- `+ 新規登録` ボタン（soleil）

> **デマンドファネルは絞り込みには使えるが、入力はできない。** ステージと流入元から
> システムが毎回決め直す導出値のため（2026-08-08）。作成・編集の画面では現在値の表示のみ。

#### 5.1.3 作業フロー: リード新規登録

1. `/leads` で `+ 新規登録` をクリック → `/leads/new` へ遷移。
2. 以下を入力する（★は必須）。
   - **★ リード名**
   - **★ ステージ** / **★ ステータス**（ステータスの選択肢はステージで絞り込まれる）
   - **★ 事業者種別**（法人／個人などの判別。会社名を入れると既定の種別が自動で入る）
   - **★ 社内担当者（主）**（初期値はログイン中の自分）。社内担当者（副）は複数選べる
   - 事業者情報・連絡先（登録済みならここで選ぶ。未登録なら「会社名」に書く）
   - 会社名・フリガナ・代表者名・法人番号・代表電話・企業 URL・従業員数・資本金
     （企業規模は従業員数と資本金から自動判定される）
   - 担当者情報（姓／ミドルネーム／名とそれぞれのカナ・部署・役職・メール・担当者電話）
   - 大分類セグメント／小分類セグメント・リードソース
3. 「保存」でリード詳細へ移動し、新しいレコードが表示される。

> デマンドファネル・温度感・スコアは入力しない。ステージや流入元・スコアリングルールから
> システムが決める（§12）。**ディールが必要なステージは新規作成では選べない**（§5.1.4）。

#### 5.1.4 作業フロー: リード育成（ステージ遷移）

1. 一覧からリード名をクリック → `/leads/[id]` 詳細画面。
2. 詳細画面右上「編集」→ `/leads/[id]/edit` へ遷移。
3. ステージ／ステータス／温度感を更新して保存。
4. 保存ごとに `lead_activities` に「ステージ変更」の履歴が記録される。

##### ステージを進めるための条件（2026-08-04 から）

**ステージは「実体が伴っていること」が条件になる。** 満たしていない場合は保存が拒否され、
何が足りないかが表示される。

| ステージ | 進めるための条件 |
|---|---|
| リード獲得 / ナーチャリング / リード選定 | なし |
| ディール | ディールがあること（**保存時に自動で作られる**） |
| オポチュニティ | ディールがあること（同上） |
| **取引先** | ディールがあり、**そのディールに契約が登録されている**こと |
| デッド | なし |

> 表のステージ名は 2026-08-10 時点の本番マスタの値。管理画面（各種設定 → ステージ・ステータス）で
> 改名できるため、名前が変わっていたら画面の表示を正とする。**条件そのものはマスタの
> 「ディール必須」「契約必須」の設定で決まり**、名前には依存しない。

- **「取引先」へ直接は進めない。** ディール・契約が無いまま成約済みにできてしまうため
- **新規作成では ディール 以降を選べない。** ディールが不要なステージで作成し、ディール化のタイミングで進める
- **リードが参照しているディール・契約は削除できない。** 先にリードのステージを下げる
- **契約の紐づけ解除も同じ扱い。** リードが参照している唯一の契約は、ディールから外せない
  （契約を消していなくても、そのディールから契約が無くなるため）

> 契約の登録・ディールへの紐づけ・紐づけ解除の手順は **§6.3 契約** にまとめてある。

「取引先」は 2026-08-04 に「Customer」から改称した。**顧客とは限らず、仕入れ先や協業
パートナーのこともある**ため、関係の方向を名前で決めない。方向は取引先の「区分」が表す。

#### 5.1.5 作業フロー: 社内対応（Lead Activity）の記録

1. リード詳細画面の「社内対応」タブ。
2. `+ 対応を記録` をクリックし、モーダルで以下を入力。
   - 対応種別（メール／電話／訪問／打合せ／その他、マスタ `lead_activity_types` で管理）
   - 件名・本文
   - 実施日時
3. 保存すると履歴に追加される。履歴は時系列降順で表示。

#### 5.1.6 作業フロー: Deal 昇格（最重要）

リードがディール化したら **ディール** または **オポチュニティ** ステージへ遷移させる。
このときシステムが以下を**自動で**生成する。

```
Lead（ディール / オポチュニティ への遷移を保存）
  └─ 事業者情報を用意（法人番号 → メールドメイン → 住所+名称 → 名称 の順に名寄せし、
     既にあればそれを使う。無ければ作る）
  └─ 連絡先を作成（電話・メールがあれば併せて登録）
  └─ ディールを作成（相手先は事業者情報・連絡先で示す）
  └─ leads の promoted_deal_id / promoted_company_id 等を更新
```

> **取引先（Account）はここでは作られない。** 取引先は契約が成立したときにだけ作られる。
> ディールの相手先は事業者情報・連絡先で示され、契約後に取引先へ切り替わる。

**昇格手順**:

1. リード編集ページを開く。
2. ステージを ディール か オポチュニティ に変更する。
3. 以下の必須項目が埋まっていることを確認。埋まっていなければ保存時にエラーになる
   （エラーは入力欄の名前で返るので、指された欄を埋める）。
   - **リード名**
   - **事業者種別**（法人 / 個人の判別）
4. 「保存」をクリック。**ディールが作られてからリードが更新される。**
5. 成功時、`promoted_deal_id` がセットされ、**再昇格は不可**（二重生成防止）。
6. 失敗時はエラーが表示され、**ステージは元のまま変わらない**。作りかけのデータは残らない。

> 昇格後も Lead 側の情報は編集できる。ディールの進捗は Deal 側で記録する。

#### 5.1.7 注意点

- **リード段階でも事業者情報・連絡先に紐づけられる**（2026-08-08）。登録済みの相手なら
  作成・編集画面で選んでおくと、昇格時に新しい事業者情報を作らずその相手に寄せられる。
  未選択なら昇格時に作られる
- 同じ法人番号の事業者情報が既にある状態でも**昇格は止まらない**。事業者情報 1 : リード N
  が正しい形のため。作成時に法人番号が重複したときは、リードは作成したうえで画面に警告を出す
- スコア・温度感はマスタ（スコアリングルール／スコア→温度感 変換ルール）に応じて自動計算される（§12）。

### 5.2 キャンペーン（`/campaigns`）

#### 5.2.1 できること

- メルマガ・イベント・広告などキャンペーン単位でリードをグルーピング。

### 6.3 契約（`/contracts`）

#### 6.3.1 できること

- 契約情報（紙面／電子／口頭）を管理。
- **どのディールにも紐づかない契約を登録できる**（2026-08-08）。先に契約書だけ届いていて、
  どのディールのものか後から決める場合に使う。
- **manager / admin のみアクセス可能**（member には一覧メニュー自体が非表示）。

#### 6.3.2 作業フロー: 契約登録

1. `/contracts` → `+ 新規登録`。ディールの編集画面の「契約を新規作成」から入ると、
   そのディールが選ばれた状態で開く。
2. 以下を入力する（必須の欄はない。分かっているものから埋める）。
   - **ディール**（**未選択のままでも登録できる**。あとからディールの編集画面で紐づけられる）
   - **契約書名**（文書そのものの名前。契約「名」は入力しない。§6.3.4）
   - **金額**（2026-08-08 に契約側へ持たせた項目。契約名の一部にもなる）
   - 契約方法（紙面／電子／口頭）・契約種別（マスタ `contract_types`）・契約内容
   - 契約相手先（区分（法人／個人）・相手先の事業者情報・相手先の連絡先（個人）・先方窓口担当）
   - 日程（契約送付日・サインバック日・契約締結日・契約開始日・契約終了日・解約日）
   - 原本 URL・契約書 URL・登録者
3. 保存。`contract_code` が自動発番される。

#### 6.3.3 作業フロー: ディールとの紐づけ

| やりたいこと | どこで |
|---|---|
| ディールに新しい契約を登録する | ディールの編集画面 →「契約を新規作成」 |
| ディールを決めずに契約を登録する | 契約の新規作成で「ディール」を空のままにする |
| すでにある契約をディールに紐づける | ディールの編集画面 →「既存の契約を紐づける」 |
| 紐づけを外す | ディールの編集画面の各行 →「紐づけ解除」／契約詳細の「ディール」欄 |

- **候補に出るのは、どのディールにも紐づいていない契約だけ。** 他のディールの契約を
  横取りしないため。移したいときは、まず元のディールで紐づけを解除する
- **紐づけ・解除は「保存」を押さなくてもすぐ反映される**（セクションに「すぐ反映」と出る）
- **解除しても契約は消えない。** どのディールにも紐づかない状態に戻るだけで、
  あとから同じディールにも別のディールにも紐づけ直せる
- 契約を紐づけると、そのディールに取引先がまだ無ければ**自動で作られる**。
  **解除しても取引先は残る**
- リードのステージが契約を要求している場合、その契約はディールから外せない（§5.1.4）

#### 6.3.4 契約名は自動で付く

契約名は入力しない。保存すると次の形で自動的に作られる。

```
契約締結日_契約書名_契約種別_金額_契約ID
例: 20260807_業務委託基本契約書_基本契約_1200000_CTR-000123
```

- **入力するのは「契約書名」**（文書そのものの名前）。契約名はそれを含んだ長い名前になる
- 締結日・契約種別・金額のうち**未入力のものは飛ばして**繋がる
- 契約締結日・契約書名・契約種別・金額を直して保存すると、**契約名も一緒に更新される**
- 一覧・変更履歴に出るのはこの契約名。横断検索は契約名・契約書名・契約コードのどれでも引ける（§3.2）

## 7. 顧客情報（連絡先・事業者情報・取引先・タレント）

### 7.1 エンティティ間の関係（要点）

```
事業者情報（法的実体）─ 1:N ─ 取引先（法人）─ N:M ─ 連絡先（individual）
                        ↘        ↑ account_contacts
事業者情報 ─ 1:N ─ 連絡先（corporate_rep / employee、直接紐付き）
                                                       ↓
                                                    タレント（1:1）
```

- `contact_type` が **`corporate_rep` / `employee`** → 事業者情報に直接紐付く。
- `contact_type` が **`individual`** → `account_contacts` を介して取引先に紐付く。

#### 取引先が作られるタイミング（2026-07-31 変更）

取引先は契約主体なので、**契約が成立するまで作られない**。

```
リード ─取込→ 事業者情報 + 連絡先        名刺はリードであると同時に連絡先
      ─昇格→ ディール（取引先なし。事業者情報／連絡先で相手を示す）
      ─契約→ 取引先が自動作成され、ディールに紐付く
```

- 名刺データを取り込むと、その時点で**事業者情報と連絡先が作られる**。連絡先一覧・横断検索から探せる
- 法人の名寄せは**メールドメイン**を最優先で見る。事業部別・旧ドメインがある場合は事業者情報の編集画面で複数登録しておくと精度が上がる（フリーメールは登録不可）
- ディール一覧の「取引先」欄は、取引先が未作成なら事業者情報名（または連絡先名）を表示する
- 契約を登録すると取引先が自動作成され、ディールの相手担当者が主担当として紐付く。手動で作る必要はない
- **手動でディールを作る場合も取引先は選ばない**（2026-08-08。作成画面から欄自体が外れている）。
  相手は事業者情報・連絡先で示し、取引先は契約を登録した時点で作られる（§6.1.3）

### 7.2 事業者情報（`/companies`）

#### 7.2.1 作業フロー: 新規登録

1. `/companies` → `+ 新規登録`。
2. 入力項目（★は必須）。
   - **★ 事業者名**（表示・検索・名寄せの正本。法人は会社名、個人事業主は屋号か個人名）
   - 会社名（法人のとき。事業者名と同じなら空でよい）／屋号名（個人事業主のとき）
   - フリガナ（事業者名から下書きが自動で入る。人が入れた値は上書きしない）
   - 代表者名（法人のときだけ表示。文字列。**連絡先への紐づけは作成後に詳細画面から選ぶ**）
   - 事業種別（マスタ `corporate_types`、例: 株式会社／合同会社／個人事業主）
   - 法人番号（13 桁。**個人事業主では欄自体が出ない**。入力するとインボイス登録番号を `T+法人番号` で自動補完）
   - **★ ステータス**（`company_statuses`）
   - リードソース
   - **社内担当者**（初期値はログイン中の自分）
   - インボイス登録番号・代表電話・FAX・ホームページ URL・メモ
3. 保存 → 詳細画面。住所は作成後に編集画面から登録する（本社・支店・請求先など複数可）。

##### 個人事業主は本人の連絡先も同時に作る

事業種別で**個人事業主**を選ぶと「事業主（本人の連絡先）」カードが現れる。
個人事業主は定義上本人が必ずいるため、ここで連絡先ごと作る（法人ではこのカードは出ない。
法人は代表者と窓口担当者が別人でありうるため、作成時に 1 人へ決め打たない）。

- チェックは**既定でオン**。オンのときは**姓・名が必須**（セイ・メイは任意）
- 保存すると連絡先が同時に作られ、その事業者の**事業主・主担当**に設定される
- 屋号が氏名と同じ場合も、ここには本人の氏名を入れる
- チェックを外して作ってもよい。その場合は連絡先が作られないので、あとから連絡先を登録し、
  詳細画面の「事業主」欄で紐づける

#### 7.2.2 作業フロー: 事業者情報から派生して作成

事業者情報詳細画面から以下を作成できる（親 → 子方向、`feedback_crud_scope_strict.md` 準拠）。

- `連絡先を追加`（この事業者情報が所属先として選ばれた状態で開く）
- `ディールを追加`（この事業者情報が相手先として選ばれた状態で開く）
- `リードを追加`（この事業者情報が選ばれた状態で開く。**事業者情報 1 : リード N**）

詳細画面には、その事業者に紐づく**リードの一覧**（リード名・ステージ・デマンドファネル）と
ディール・連絡先の一覧が並ぶ。同じ会社から複数のリードが来ても事業者情報は 1 つに寄せる。

#### 7.2.3 事業主・代表者・主担当の紐づけ

代表者（個人事業主のときは「事業主」）と主担当は、**詳細画面でその場で選んで保存できる**。
いずれも文字列ではなく**連絡先レコードへの紐づけ**なので、連絡先の情報を直せば表示も追随する。

### 7.3 取引先（`/accounts`）

#### 7.3.1 作業フロー: 法人取引先新規登録

1. `/accounts` → `+ 新規登録` → 取引先種別「法人」を選択。
2. 事業者情報を既存から選択（または、親の事業者情報詳細から作成すれば自動選択）。
3. 取引先名・ステータス・社内担当者を入力（**社内担当者の初期値はログイン中の自分**）。
4. 保存。

> 取引先は契約を登録した時点で自動的に作られる（§7.1）。手で作るのは、契約より前に
> 取引先として管理したい特別な事情があるときに限る。

#### 7.3.2 作業フロー: 個人取引先新規登録

1. `/accounts` → `+ 新規登録` → 取引先種別「個人」を選択。
2. `+ 連絡先を追加` から `individual` 連絡先を選ぶ／新規作成する。
3. 保存。`account_contacts` に紐付け行が作成される。

### 7.4 連絡先（`/contacts`）

#### 7.4.1 入力項目

`/contacts` → `+ 新規登録`（事業者情報・取引先の詳細から入ると、その相手が選ばれた状態で開く）。
★は必須。

| セクション | 項目 |
|---|---|
| 氏名 | **★ 姓** / ミドルネーム / **★ 名** / フリガナ（姓・ミドル・名） |
| 基本情報 | **★ ステータス** / 種別（個人・法人代表・法人従業員・その他）/ 所属事業者情報 / 担当者（初期値はログイン中の自分）/ 部署 / 役職 / 生年月日 / 血液型 / リードソース |
| 連絡手段 | メール・電話・**SNS・チャット**（いずれも複数登録可。§7.4.2） |
| 住所 | 郵便番号 / 都道府県 / 市区町村 / 町名・番地 / 建物名・部屋番号 / 種別 |
| その他情報 | LINE User ID |
| メモ | 社内メモ |

- **種別で紐づけ先が決まる。** 法人代表 / 法人従業員は所属事業者情報に直接紐づく。
  個人は取引先に `account_contacts` を介して紐づく（取引先の詳細から作成すればその場で紐づく）
- 氏名・連絡手段・住所は**まとめて 1 回で保存される**（途中まで作られて残ることはない）
- 生年月日を入れると、保存時にポテンシャル診断（`potential_number` / 星座）が自動算出される（§7.5）

#### 7.4.2 連絡手段（メール・電話・SNS・チャット）

**メールも電話も複数登録できる。** 「メールを追加」「電話を追加」で行を足し、
それぞれに種別（メール: 勤務先／個人／その他、電話: 勤務先／携帯／自宅／FAX／その他）を付ける。
★アイコンが**主メール／主電話**で、行の★を押すと切り替わる（1 件目は自動で主になる）。

**SNS・チャット**は「SNS・チャットを追加」で足す。サービスを選ぶと、そのサービスに応じて
入力欄と説明が変わる。

| 欄 | 内容 |
|---|---|
| サービス | Chatwork / Slack / LINE / X / Messenger / Instagram / LinkedIn / その他 |
| ワークスペース | **Slack のときだけ出る**（ワークスペース ID）。他のサービスでは表示されない |
| ID | サービスごとに入れるものが違う（例: Chatwork はダイレクトチャットのルーム ID、Slack はメンバー ID） |
| 表示名 | 同じサービスに複数登録するときの区別用（任意） |

- サービスを選ぶと欄の下にそのサービス向けの説明が出る。何を入れるか迷ったらそれを読む
- 登録すると連絡先の詳細から**その相手との個別のやり取り**を開ける
  （LinkedIn だけは DM の直リンクが無いためプロフィールが開く）
- 空の行は無視されるが、途中まで入れた行は保存前に止められる（サービスと ID の両方が要る）
- 作成時に入れなくても、あとから編集画面で追加できる

> SNS・チャットのサービス一覧はマスタ（`social_services`）で持つが、
> **マスタ管理画面のタブには無い**。追加・変更が必要なときはシステム管理者へ依頼する。

### 7.5 タレント（`/talents`）

#### 7.5.1 できること

- 連絡先と 1:1 で紐付く人材特性情報。
- スキル・経歴・ポテンシャル診断（動物占いベース）・星座。

#### 7.5.2 作業フロー: タレント登録

1. `/talents` → `+ 新規登録`。
2. 紐付け先連絡先を選択。
3. 生年月日を入力 → **保存時に自動で以下が算出される**。
   - `potential_number`（1〜60）
   - `constellation`（12 星座）
4. スキル（マスタ `skills` から複数選択）、経歴、メモを入力。
5. 保存。

> ポテンシャル診断は `applyBirthDateDiagnosis` が内部で呼ばれ、マスタ `number_diagnosis` / `constellation_fortune_telling` から結果を引く。マスタ未投入時はエラーになる。

## 9. 編集・削除の共通ルール

`feedback_edit_flow_unified.md` / `project_delete_policy.md` に基づく全画面共通のルール。

### 9.1 詳細 → 編集 → 保存の統一フロー

- 詳細ページ（`/xxx/[id]`）は**閲覧専用**。インライン編集はしない。
- 右上「編集」ボタン → 編集ページ（`/xxx/[id]/edit`）に遷移。
- 編集ページで「保存」「キャンセル」「削除」を行う。
- 保存後は詳細ページへ戻る。

### 9.2 削除（論理削除）

- 削除ボタンは**編集ページ内**に配置。独立した「危険ゾーン」セクションは置かない。
- クリック時は確認モーダルが表示される（「本当に削除しますか？」）。
- 実行すると `deleted_at` に現在時刻をセット。一覧からは即座に消える。
- 関連する履歴・子レコードは保持される。

### 9.3 復元

- admin のみ `/admin/deleted` にアクセス可能。
- エンティティ別タブから、削除日時・削除者を確認しつつ復元できる。

### 9.4 物理削除について

- **画面から物理削除する操作は提供しない**（監査証跡確保のため）。
- ただし放置による肥大化を防ぐため、**論理削除から 90 日経過した行は自動処理（pg_cron）が物理削除する**。誤削除は 90 日以内に `/admin/deleted` から復元すること。
- ディールの削除は admin 限定（§6.1.7）。member / manager はクローズ（失注）で対応する。

## 10. アクセス制御と見え方

### 10.1 多層防御

全ての書き込み操作は以下 3 層で保護されている（ユーザーはこれを意識する必要はない）。

1. **Middleware**: 未認証は `/login` へ強制リダイレクト。
2. **Server Action**: 認証チェック + ロールチェック + オーナーチェック。
3. **RLS**: Supabase の Row Level Security で DB レベル制御。

### 10.2 member から見える範囲

- `owner_user_id = 自分` のレコードのみ一覧に表示される。
- 他人のディール URL を直接叩いても取得できず「見つかりません」表示。
- ダッシュボードの集計も自分持ち分のみ。

### 10.3 manager / admin から見える範囲

- 全件表示。フィルタでメンバー別に絞り込み可能。
- manager は契約の CUD 可。マスタは不可。
- admin はすべて可能。

### 10.4 一括処理（ジョブ）の権限

時間のかかる一括処理は投入と実行を分けている（§12.5）。**投入できるかどうかは種別ごとに違う。**

| ジョブ | member | manager | admin |
|---|---|---|---|
| 統合候補の一括検出 | × | ○ | ○ |
| 全リードのスコア再計算 | × | × | ○ |

自分が投入できない種別のジョブは、状況（実行中・結果）も見えない。

## 11. よくあるトラブルと対処

| 症状 | 原因 | 対処 |
|---|---|---|
| 「リード名を入力してください。ディールに昇格するには必要です」／「事業者種別を選択してください。ディールに昇格するには必要です」 | 昇格に必要な項目が空 | メッセージが指す欄を埋めてから保存し直す（欄の名前がそのまま出る） |
| 「〜へ進めるにはディールが必要です」／「〜へ進めるには契約が必要です」 | ステージが要求する実体が揃っていない | ディール（さらに必要なら契約）を先に登録してからステージを進める（§5.1.4） |
| 「〜はディールが必要なステージのため、新規作成では選べません」 | 新規リードにディールは無い | ディールが不要なステージで作成し、ディール化するタイミングで進める |
| 「このリードはすでにディールに昇格済みです」 | 二重昇格防止の想定挙動 | 既に生成されたディールを編集する。リード側は参照専用 |
| ディール一覧に削除ボタンがない | 削除は**編集ページ内**にあり、admin 限定 | admin なら編集ページから削除（契約が紐づいていると不可）。それ以外は失注ステージへの遷移で「取り消し」を表現するか admin へ依頼 |
| 他メンバーのディールが見えない | member 権限のため | manager へロール変更を依頼する |
| `/admin` にアクセスしても 404 | admin 以外はメニュー非表示・URL アクセスも拒否 | admin への昇格を依頼する |
| タレント保存時に「ポテンシャル診断マスタが見つかりません」 | `number_diagnosis` / `constellation_fortune_telling` 未投入 | admin に連絡してマスタ投入を依頼 |
| カンバンでドラッグしてもステージが戻る | ネットワークエラーまたは権限不足 | ブラウザのコンソールを確認。それでも解決しない場合は管理者へ連絡 |
| 検索結果が出ない | フィルタが残存している | `フィルタをクリア` ボタンで全解除 |

## 12. リードスコア週次再計算（バッチ運用）

### 12.1 概要

リードのスコア・温度感は、Lead の作成・更新・顧客行動登録のたびにリアルタイム再計算される。
これに加えて、スコアリングルール（マスタ）や企業規模マスタが管理者によって変更された場合、
その変更を全リードに一括反映するために **週次バッチ** が自動実行される。

### 12.2 実行スケジュール

| 項目 | 内容 |
|---|---|
| 実行タイミング | 毎週日曜 03:00（JST） |
| UTC 換算 | 毎週土曜 18:00（UTC） |
| cron 書式 | `0 18 * * 6` |
| pg_cron jobname | `recalculate_lead_scores_weekly` |

### 12.3 処理内容

1. `leads` テーブルの全有効レコード（`deleted_at IS NULL`）をループ
2. 各リードについて企業規模を再判定し、マスタ変更があれば `company_size_id` を更新
3. `recalculate_lead_score` を実行し、スコア・温度感・内訳（breakdowns）を更新

### 12.4 ログ確認

Supabase Dashboard > Database > Logs（NOTICE レベル）で以下のメッセージを確認できる:

```
[recalculate_all_lead_scores] N リードの再計算を完了
```

### 12.5 手動実行（画面から。ジョブ方式）

スコアリングルールを変更した直後に即時反映したい場合は、**画面のボタンから実行する**
（2026-08-09。SQL を直接実行する運用はやめた）。

1. `/admin` →「リード・マーケティング」→「スコアリングルール」タブを開く。
2. 見出しの右にある **「全件を再計算」** を押す。
3. 「再計算の順番を待っています」→「全 Lead のスコアを再計算しています」と表示が進む。
4. 終わるとトーストで「N 件のリードを再計算しました」と出る。

- **この画面を閉じても再計算は続く。** あとで開き直せば途中経過と結果を確認できる
- 実行できるのは **admin のみ**（§10.4）
- 失敗した場合は赤い枠に理由が出る

#### ジョブ方式の 3 操作

件数に比例して時間がかかる操作は、**押した瞬間に実行するのではなく順番待ちの列に積む**。
実行役は毎分動くため、押してから着手まで最大 1 分ほど空く。どれも画面を閉じても進み、
開き直すと状況が復元される。

| 操作 | 場所 | 実行できる人 |
|---|---|---|
| 名刺データの取込 | `/admin/leads/import` | admin |
| 統合候補の一括検出（「候補を洗い直す」） | `/contacts/merge-candidates` | manager / admin |
| 全リードのスコア再計算（「全件を再計算」） | `/admin` → スコアリングルール | admin |

> **統合候補の検出は名刺取込の中でしか自動では走らない。** 取込以外の経路で増えた重複は
> 「候補を洗い直す」で拾う。終わると「統合候補が N 件見つかりました」または
> 「新しい統合候補はありませんでした」と出る。

### 12.6 注意事項

- 実行中は `statement_timeout` が無効化されるため、Lead 件数が非常に多い場合でも完走する
- マスタ（スコアリングルール等）の変更は翌週バッチで自動反映。緊急の場合は §12.5 で対応する
- バッチジョブの登録状況は `SELECT * FROM cron.job WHERE jobname = 'recalculate_lead_scores_weekly';` で確認できる

## 13. バックアップと復旧

Supabase Free プランには PITR（ポイントインタイムリカバリ）が無い。
そのため GitHub Actions で日次の論理バックアップを取得している。

### 13.1 バックアップの仕組み

| 項目 | 内容 |
|---|---|
| ワークフロー | `.github/workflows/db-backup.yml` |
| 実行時刻 | 毎日 JST 03:00（UTC 18:00）。手動実行も可 |
| 形式 | `pg_dump --format=custom`（`pg_restore` で部分復元が可能） |
| 保管先 | GitHub Actions のアーティファクト（保持 30 日） |
| 必要な secret | `SUPABASE_DB_PASSWORD`（DB パスワードのみ。接続文字列ではない） |

取得後に `pg_restore --list` で主要テーブル（leads / deals / contacts / companies / accounts / entity_change_logs）が
含まれることを検証している。空ダンプがそのまま保管されるのを防ぐため。

このジョブは毎日 DB に接続するため、**無操作による Supabase プロジェクトの一時停止も同時に防いでいる**。

### 13.2 復旧手順

1. Actions の該当実行からアーティファクトをダウンロードして展開する
2. 復旧先の接続文字列を用意する（本番へ直接戻す前に、必ず検証用プロジェクトで試すこと）
3. 全体を戻す場合:

```bash
pg_restore --no-owner --no-privileges --clean --if-exists   --dbname "<接続文字列>" iterra-hub-<日時>.dump
```

4. 特定テーブルだけ戻す場合:

```bash
pg_restore --no-owner --no-privileges   --table=leads   --dbname "<接続文字列>" iterra-hub-<日時>.dump
```

### 13.3 運用上の注意

- 保持は 30 日。四半期や年次で残す必要がある場合は、ワークフロー内にコメントしてある R2 退避を有効にする
- 復旧点は最大 24 時間前。それより細かい復旧が必要な業務が出てきた場合は、有償プランの PITR を検討する
- `entity_change_logs`（§ 変更履歴）はトリガーで全変更を記録しているため、
  誤更新の調査は復旧より先にこのテーブルを確認する方が早い

## 14. 外部連携（Gmail・Google コンタクト・freee 会計）

どの連携も「接続」してから「同期」を行う。接続先のデータを勝手に書き換えることはなく、
**CRM が正**として扱う（freee 会計だけは項目ごとにどちらを正にするか選べる）。

### 14.1 Gmail 連携（`/profile`）

連携すると、そのアカウントの送受信が連絡先の**アクティビティ**として並ぶ。
取り込むのは件名・相手・日時だけで、**本文と添付は CRM に保存しない**（中身は Gmail 側で開く）。

1. `/profile` を開く（ヘッダーのユーザーメニュー →「プロフィール設定」）。
2. 「Gmail 連携」カードの「アカウントを連携」→ Google のログイン画面で許可する。
3. 接続すると一覧に表示される。「同期」で取り込みを開始する。
4. 連絡先詳細の「アクティビティ」に、件名・日時・送受信の向きが並ぶ。
   クリックすると Gmail が別タブで開く。
5. 「解除」で連携を止める。取り込み済みのやり取りは履歴として残る。

> 環境変数が未設定の環境では「Gmail 連携が未設定です」と表示され、接続ボタンは出ない。

### 14.2 Google コンタクト連携（`/profile`）

CRM の連絡先を Google コンタクトの **「ITERRA CRM」グループ**へ同期する。
スマホの電話帳や Gmail の宛先補完に相手の名前が出るようになる。
**触るのはこのグループの中だけ**で、個人の連絡先には手を付けない。
社内メモ・診断結果・ステータスは同期しない。

1. `/profile` の「Google コンタクト連携」カードで「Google と連携する」。
2. 連携時に Google から「連絡先の表示、編集、ダウンロード、完全な削除」の許可を求められる。
   Google の連絡先スコープは 1 段階しかなく、書き込むにはこれを許可する必要がある。
   実際に作成・更新・削除するのは「ITERRA CRM」グループに入れた連絡先だけ。
3. 「同期」で登録・更新・削除を反映する。件数が多い場合は 1 回の上限で打ち切られ、
   「もう一度同期を押すと続きから進みます」と案内される。
4. 「解除」で同期を止める。Google 側の連絡先は残る
   （消したい場合は Google の画面で「ITERRA CRM」グループごと削除する）。

> 会社の Google アカウントで連携する。環境変数が未設定の環境では接続ボタンは出ない。

### 14.3 freee 会計連携（`/admin/freee`・admin 専用）

freee 会計にある取引先を CRM へ取り込み、事業者情報と突き合わせる。
**freee 側のデータを自動で書き換えることはない。**
書き換えるのは、差分画面（§14.3.4）で人が「CRM → freee」を選んで確定した項目と、
事業者の追加登録（§14.3.3）だけ。定期同期そのものは取り込みのみ。

#### 14.3.1 接続と同期

1. `/admin/freee` を開く（サイドバーの「管理」→「freee 連携」）。
2. 「freee と接続する」→ freee のログイン画面で事業所へのアクセスを許可する。
3. 接続後は事業所名・接続日時・最終同期日時・最終の全件同期日時が表示される。

| ボタン | 内容 |
|---|---|
| 今すぐ同期 | 前回同期日以降に更新された取引先だけを取り込む（差分） |
| 全件同期（削除も検出） | 全件を取り直す。**freee 側で削除された取引先が分かるのはこれだけ** |
| 接続を解除 | 以後の同期を止める。取り込み済みのデータと紐付けは残る |

本番では日次（差分）・週次（全件）で自動実行される。手動同期は確認や急ぎのとき用。
環境変数が未設定の環境では「未設定です」と出て接続ボタンは表示されない。

「前回の同期でエラーが出ています」と赤い枠が出たら、文言のとおりに対処する。
「接続が切れています」の場合は接続し直す（freee 側でアプリの許可を取り消した場合など）。

#### 14.3.2 突合（`/admin/freee/partners`）

**インボイス登録番号が一致した取引先は自動で紐付く。** それ以外は状態が「未紐付け」で並ぶので、
行を開いて詳細と候補を見ながら次のいずれかを選ぶ。

| 操作 | いつ使うか |
|---|---|
| 候補の「これに紐付ける」 | CRM に同じ相手が既にいる。候補は名称・メールドメイン・電話の一致から出る |
| 「事業者情報として登録」 | CRM にまだいない。事業者情報を新しく作って紐付ける |
| 「対象外にする」 | CRM に持つ必要が無い相手（税務署・銀行など） |

- **取引先（Account）はここでは作られない。** 取引先は契約が成立したときにだけ作られる
  仕組みのため、ここで作るのは事業者情報まで
- 「紐付け状態」の絞り込みで、確定済み・自動・対象外も確認できる。誤って紐付けたときは
  その行を開いて「紐付けを解除する」（対象外にしたものは「対象外を取り消す」）
- インボイス番号が CRM と freee で食い違う行には警告が出る。**CRM の値が正**として扱い、
  自動では紐付かない。どちらが正しいかを確認して事業者情報側を直す
- freee 側で使用停止・削除された取引先は既定で隠れている。「使用停止・削除」を「含める」に
  すると表示される

#### 14.3.3 連携する事業者の追加（`/admin/freee/register`）

CRM にあって freee に無い事業者情報を、freee 側へ新しく登録する画面。
一覧を開いて行を展開すると freee 側の似た取引先が候補として出るので、
**既にあるなら新規登録ではなく紐付けを選ぶ**
（freee は取引先名の重複を許すため、確認せずに作ると表記ゆれで同じ相手が 2 つできる）。

- 候補が無ければ「freee に登録する」で新規登録する
- 登録すると取引先コードに CRM の事業者コード（例: `CMP-…`）が入り、以後はこのコードで自動的に突合される
- **取引先コードは登録のときにしか入れられない。** 作り直しでは直せないため、
  似た取引先が無いか必ず確認してから登録する

#### 14.3.4 差分の確認と反映（`/admin/freee/sync`）

取り込んだ freee の値と CRM の値を項目ごとに見比べ、どちらを正として反映するか選ぶ画面。
**既定はすべて「CRM → freee」。** 会計側の修正を採りたい項目だけ「freee → CRM」に切り替える。
反映しない項目は「触らない」のままにしておく。

- **「CRM → freee」を選んだ項目は freee 側が書き換わる。** 反映は 1 相手ずつ、
  「この相手の差分を反映」で確定する
- **担当者名**は freee 側の値をそのまま取り込めない（氏名の切れ目が分からず、
  同名の別人に紐づく恐れがあるため）。「この名前の連絡先を探す」で候補を出し、人が選んで紐づける
- **担当者メール**は、同じ人が 2 社の担当者で会社ごとに使い分けている場合に備え、
  行の「連携に使うメール」欄からその場で選べる（連携プロファイルへ直接保存される）
- **取引先コード**はどちらへも反映できない。freee の更新 API がコードを受け付けず（登録時のみ）、
  事業者コードは CRM が採番するため。揃えたい場合は freee の画面で直接入力する
- どちらの向きにも直せない項目は **「この項目は突き合わせない」** で対象外にできる。
  対象外は差分一覧から消えるため、**戻す入口は画面上部の「突き合わせ対象外にした項目」に置かれている**。
  値そのものは変えない

#### 14.3.5 連携プロファイル（事業者情報の詳細・admin 限定）

freee へ渡す値をどのレコードから取るかを、事業者情報ごとに選べる設定。
**値そのものではなくレコードを選ぶ**ため、CRM 側の情報を直せば連携値も追随する。
対象は**担当者・担当者メール・電話・住所・口座**の 5 項目。

- 未選択は「既定に従う」（主担当・主メール・主住所・主口座・代表電話）
- 担当者を選び直すとメールの選択は外れる（別人のメールを送らないため）。
  担当者の候補はその事業者に関わる連絡先（所属または兼務）だけ
- 同じ人が 2 社の担当者で、会社ごとにメールを使い分けている場合に必要になる
  （主メールは連絡先に 1 つしか立たないため）
