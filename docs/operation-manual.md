## 1. はじめに

### 1.1 何ができるシステムか

ITERRA CRM は「リードの獲得 → 育成 → 商談昇格 → 受注 → プロジェクト／契約管理」までを 1 画面で追う統合 CRM である。
従来の CRM に加え、**マーケティング（マーケティングオートメーション）** と **営業（セールスフォースオートメーション）** を同居させている。

- **マーケティング層**: リードの温度感・ステージ・コール履歴・キャンペーン紐付け。
- **営業層**: 商談のパイプライン進捗・プロジェクト・契約。
- **顧客情報層**: 連絡先・法人情報・取引先・タレント情報。
- **ポテンシャル診断**: 生年月日から自動算出する性質分析（タレント／連絡先）。

### 1.2 本マニュアルの読み方

各機能の章は **「何ができるか」→「画面」→「作業フロー」→「注意点」** の順で構成している。
はじめて触る場合は第 2〜4 章 → 自分の業務に関連する章の順で読むと迷わない。

## 2. ログインとロール

### 2.1 ログイン

1. ブラウザで CRM の URL にアクセスする。
2. 未認証の場合、自動的に `/login` にリダイレクトされる（Middleware による制御）。
3. メールアドレスとパスワードを入力してログインする。
4. 認証成功後、ロールに応じた初期画面（ダッシュボード）に遷移する。

### 2.2 ロールごとにできること

| ロール | 参照範囲 | 主要な操作 | マスタ管理 | 契約操作 |
|---|---|---|---|---|
| **member** | 自分が社内担当者のレコードのみ | 連絡先/取引先/商談等の CRUD（自分持分） | × | × |
| **manager** | 全件 | 全エンティティの CRUD、契約の CUD | × | ○ |
| **admin** | 全件 | 全操作（マスタ CRUD、論理削除、削除済みの復元） | ○ | ○ |

> 権限外の操作はボタン自体が表示されない／Server Action 側で拒否されるため、不正操作は発生しない。

## 4. ダッシュボード

### 4.1 何が見られるか

`/dashboard` には 6 つの KPI カードと 4 つの可視化ブロックが並ぶ。

**KPI カード（上段）**

- 進行中商談件数（`closed_at IS NULL`）
- 進行中商談の合計金額（JPY）
- 今月クローズ件数（`closed_at` が当月）
- 取引先数（アクティブのみ）
- 連絡先数（アクティブのみ）
- 法人情報数（アクティブのみ）

**可視化ブロック（下段 2×2 グリッド）**

- **パイプラインファネル**: 商談ステージごとの進行中件数を横棒グラフで表示。
- **最近の商談**: 作成日時降順で上位 5 件。コード・名前・ステージ・金額・社内担当者。
- **最近の対応履歴**: `deal_activities` の最新 5 件。種別（メール／電話／打合せ／訪問／その他）・件名・対応者・日時。
- **担当者別商談数**: 進行中商談の社内担当者別集計（件数降順）。

### 4.2 作業フロー

ダッシュボードは情報表示のみで編集操作はない。観察 → 詳細画面への遷移起点として使う。

1. 朝一でダッシュボードを開く。
2. パイプラインファネルで自分の商談分布を把握（要フィルタがないため、member は自分分のみ集計される）。
3. 最近の対応履歴で他メンバーの最新活動を確認。
4. 気になる商談があればサイドバー「商談」へ移動し、商談詳細へ遷移。

## 5. マーケティング（リード・キャンペーン）

### 5.1 リード（`/leads`）

#### 5.1.1 できること

- 見込み客情報を社名やフルネームで管理（Company / Contact にはまだ作成しない）。
- ステージ × ステータス × 温度感 × カテゴリ × 担当者で一覧を絞り込み。
- スコアによる並べ替え。
- **Opportunity ステージへの遷移で、Company / Contact / Account / Deal を自動生成**（Deal 昇格）。

> **重要**: リード段階では既存の Company / Contact と紐付けない。Deal 昇格時に初めてエンティティが作成される。`feedback_lead_opportunity_promotion.md` 準拠。

#### 5.1.2 画面構成

一覧ページ上部に以下のフィルタとアクションが並ぶ。

- 検索ボックス（氏名／社名／メール／電話の部分一致）
- ステージ・ステータス・カテゴリ・温度感・担当者のドロップダウン
- スコアでソートボタン
- `+ 新規登録` ボタン（soleil）

#### 5.1.3 作業フロー: リード新規登録

1. `/leads` で `+ 新規登録` をクリック → `/leads/new` へ遷移。
2. 以下を入力する（★は必須）。
   - **★ 氏名**（姓／名） ※名は任意
   - **★ リードソース**（例: Web 問い合わせ／イベント）
   - **★ 担当者**（社内担当者、初期値は自分）
   - 社名（任意。未入力のまま登録可能）
   - メール／電話／URL
   - カテゴリ・ステージ・ステータス・温度感
   - スコア（数値。自動算出ルールがある場合は上書きされる）
   - メモ
3. 「保存」で一覧に戻り、新しいレコードが表示される。

#### 5.1.4 作業フロー: リード育成（ステージ遷移）

1. 一覧からリード名をクリック → `/leads/[id]` 詳細画面。
2. 詳細画面右上「編集」→ `/leads/[id]/edit` へ遷移。
3. ステージ／ステータス／温度感を更新して保存。
4. 保存ごとに `lead_activities` に「ステージ変更」の履歴が記録される。

#### 5.1.5 作業フロー: 対応履歴（Lead Activity）の記録

1. リード詳細画面の「対応履歴」セクション。
2. `+ 対応を記録` をクリックし、モーダルで以下を入力。
   - 対応種別（メール／電話／訪問／打合せ／その他、マスタ `lead_activity_types` で管理）
   - 件名・本文
   - 実施日時
3. 保存すると履歴に追加される。履歴は時系列降順で表示。

#### 5.1.6 作業フロー: Deal 昇格（最重要）

リードが商談化したら Opportunity ステージへ遷移させる。このときシステムが以下を**自動で**生成する。

```
Lead（Opportunity 遷移を保存）
  └─ Step 1: Company 作成（社名がある場合）
  └─ Step 2: Contact 作成（contact_type は employee or individual）
  └─ Step 2b: 電話があれば contact_phones に INSERT
  └─ Step 3: Account 作成（法人 or 個人）
  └─ Step 4: account_contacts で Contact を紐付け
  └─ Step 5: Deal 作成（Account 紐付き、Opportunity パイプライン）
  └─ Step 6: leads テーブルの promoted_deal_id / promoted_company_id 等を更新
```

**昇格手順**:

1. リード編集ページを開く。
2. ステージを Opportunity（コード: `opportunity`）に変更。
3. 以下の必須項目が埋まっていることを確認。埋まっていなければ保存時にエラーになる。
   - **lead_name**（リード氏名 / 社名）
   - **account_type_id**（法人 / 個人の判別）
4. 「保存」をクリック。サーバー側で `promoteLeadToDeal` が実行される。
5. 成功時、`promoted_deal_id` がセットされ、**再昇格は不可**（二重生成防止）。
6. 失敗時、エラーメッセージが表示される。途中まで作成されたエンティティは自動ロールバックされる。

> 昇格後は Lead は「参照専用」扱い。以降のやり取りは Deal 側で記録する。

#### 5.1.7 注意点

- リード段階で Company や Contact を直接参照するフィールドは存在しない。誤って既存 Company を選ばせない設計になっている。
- スコアはマスタ `lead_score_thresholds` の設定に応じて自動計算される（将来拡張）。

### 5.2 キャンペーン（`/campaigns`）

#### 5.2.1 できること

- メルマガ・イベント・広告などキャンペーン単位でリードをグルーピング。
- キャンペーン × リードの N:M 関係を管理。
- 後続の「シナリオ機能（ステップメール等）」は**現時点では未実装**。土台のみ提供。

#### 5.2.2 作業フロー: キャンペーン作成

1. `/campaigns` → `+ 新規登録`。
2. 以下を入力。
   - キャンペーン名
   - 開始日 / 終了日
   - ソース（lead_sources と対応）
   - 説明
3. 保存。詳細画面で「リードを紐付け」ボタンから既存リードを複数選択できる。

## 6. 営業（商談・プロジェクト・契約）

### 6.1 商談（`/deals`）

#### 6.1.1 できること

- **カンバン / テーブルの切替**（右上アイコンで切替）。
- カンバンはステージ別 or ステータス別にグルーピング可能。
- パイプライン種別で表示を切替。
- ドラッグ & ドロップでステージを変更。
- 検索・フィルタ。

#### 6.1.2 画面構成

- 上部: パイプライン種別ドロップダウン / ビュー切替（カンバン／テーブル） / 検索 / `+ 新規登録`。
- カンバンビュー: 列＝ステージ（ or ステータス）、カード＝商談。
- カラースケール: ステージ／ステータスの `sort_order` に応じて 8 色から循環割当（カンバンカード上辺のアクセント）。

#### 6.1.3 作業フロー: 商談直接登録

> リードからの昇格以外に、既存 Account に対して新規商談を直接登録する経路もある。

1. `/deals` → `+ 新規登録` → `/deals/new`。
2. 以下を入力（★は必須）。
   - **★ 商談名**
   - **★ 取引先**（既存から選択、検索ドロップダウン）
   - **★ パイプライン種別**
   - **★ ステージ**（パイプライン選択に応じて選択肢が絞り込まれる）
   - ステータス
   - 金額・クローズ予定日
   - 社内担当者（初期値は自分）
   - メモ
3. 保存。`deal_code` が自動発番される。

#### 6.1.4 作業フロー: カンバンでのステージ遷移

1. `/deals` をカンバンビューで開く。
2. 対象カードを掴んで別列へドラッグ。ハイライト（soleil）でドロップ先を確認。
3. ドロップと同時に `deal_stage_id` が更新され、`deal_stage_histories` に履歴が記録される。
4. 失敗時は元の位置に戻り、エラートーストが表示される。

#### 6.1.5 作業フロー: 商談対応履歴の記録

1. 商談詳細 `/deals/[id]` の「対応履歴」セクション。
2. `+ 対応を記録` からモーダルで入力。
   - 種別（メール／電話／打合せ／訪問／その他）
   - 件名・本文・実施日時
3. 保存で `deal_activities` に追加される（ダッシュボードの「最近の対応履歴」にも反映）。

#### 6.1.6 作業フロー: 商談クローズ

1. 詳細 → 編集ページへ。
2. ステージを「受注」「失注」等のクローズ系へ変更、`closed_at` を入力。
3. 保存すると以降はダッシュボードの「進行中」集計から外れ、「今月クローズ」に集計される。

#### 6.1.7 注意点

- `deals` テーブルには現状 `is_active` カラムがないため、**UI から削除操作は提供していない**。取り消したい場合はクローズ（失注）扱いにする。

### 6.2 プロジェクト（`/projects`）

#### 6.2.1 できること

- 複数商談を「目的」単位でグルーピング（例: 万博プロジェクト）。
- パイプラインとは直交する軸。1 商談が複数プロジェクトに属することも可能。
- プロジェクトメンバー（CRM ユーザー）をフラットに割当。ロール区別なし。

#### 6.2.2 作業フロー: プロジェクト作成

1. `/projects` → `+ 新規登録` → `/projects/new`。
2. 以下を入力。
   - プロジェクト名
   - ステータス（マスタ `project_statuses`）
   - 責任者（1 名、初期値は自分）
   - 開始日・終了予定日
   - 説明
3. 保存。詳細画面から「商談を追加」「メンバーを追加」で関連付ける。

#### 6.2.3 作業フロー: 商談をプロジェクトに紐付け

1. プロジェクト詳細 → 「商談」タブ → `+ 商談を追加`。
2. 候補一覧から複数選択 → 保存。中間テーブル `deal_projects` に INSERT。
3. 解除は行ごとの「×」アイコンから。

#### 6.2.4 注意点

- プロジェクトと取引先は**直接のリレーションを持たない**。必ず商談経由で関連する。
- 商談担当者の自動同期はしない。プロジェクトメンバーは手動管理。

### 6.3 契約（`/contracts`）

#### 6.3.1 できること

- 商談に紐づく契約情報（紙面／電子／口頭）を管理。
- **manager / admin のみアクセス可能**（member には一覧メニュー自体が非表示）。

#### 6.3.2 作業フロー: 契約登録

1. `/contracts` → `+ 新規登録`。
2. 以下を入力。
   - 契約対象の商談（既存から選択）
   - 契約種別（マスタ `contract_types`）
   - 契約方式（`paper` / `electronic` / `verbal`）
   - 契約日・開始日・終了日
   - 金額
   - メモ
3. 保存。

## 7. 顧客情報（連絡先・法人情報・取引先・タレント）

### 7.1 エンティティ間の関係（要点）

```
法人情報（法的実体）─ 1:N ─ 取引先（法人）─ N:M ─ 連絡先（individual）
                        ↘        ↑ account_contacts
法人情報 ─ 1:N ─ 連絡先（corporate_rep / employee、直接紐付き）
                                                       ↓
                                                    タレント（1:1）
```

- `contact_type` が **`corporate_rep` / `employee`** → 法人情報に直接紐付く。
- `contact_type` が **`individual`** → `account_contacts` を介して取引先に紐付く。

#### 取引先が作られるタイミング（2026-07-31 変更）

取引先は契約主体なので、**契約が成立するまで作られない**。

```
リード ─取込→ 法人情報 + 連絡先        名刺はリードであると同時に連絡先
      ─昇格→ 商談（取引先なし。法人情報／連絡先で相手を示す）
      ─契約→ 取引先が自動作成され、商談に紐付く
```

- 名刺データを取り込むと、その時点で**法人情報と連絡先が作られる**。連絡先一覧・横断検索から探せる
- 法人の名寄せは**メールドメイン**を最優先で見る。事業部別・旧ドメインがある場合は法人情報の編集画面で複数登録しておくと精度が上がる（フリーメールは登録不可）
- 商談一覧の「取引先」欄は、取引先が未作成なら法人情報名（または連絡先名）を表示する
- 契約を登録すると取引先が自動作成され、商談の相手担当者が主担当として紐付く。手動で作る必要はない
- 手動で商談を作る場合（名刺経由でない場合）は、従来どおり取引先の選択が必須

### 7.2 法人情報（`/companies`）

#### 7.2.1 作業フロー: 新規登録

1. `/companies` → `+ 新規登録`。
2. 入力項目。
   - 社名（正式名称）
   - 法人格（マスタ `corporate_types`、例: 株式会社／合同会社）
   - 法人番号（13 桁、任意）
   - インボイス登録番号（任意）
   - 代表者名（文字列、連絡先とは紐付けない）
   - 取引先担当者（`primary_contact_id`、後から設定可）
   - ステータス（`company_statuses`）
   - 住所・電話・URL
3. 保存 → 詳細画面。

#### 7.2.2 作業フロー: 法人情報から派生して作成

法人情報詳細画面から以下を作成できる（親 → 子方向、`feedback_crud_scope_strict.md` 準拠）。

- `+ 取引先を作成`（法人取引先が自動でこの法人情報に紐付く）
- `+ 法人連絡先を作成`（contact_type=employee / corporate_rep を選択）

### 7.3 取引先（`/accounts`）

#### 7.3.1 作業フロー: 法人取引先新規登録

1. `/accounts` → `+ 新規登録` → 取引先種別「法人」を選択。
2. 法人情報を既存から選択（または、親の法人情報詳細から作成すれば自動選択）。
3. 取引先名・ステータス・社内担当者を入力。
4. 保存。

#### 7.3.2 作業フロー: 個人取引先新規登録

1. `/accounts` → `+ 新規登録` → 取引先種別「個人」を選択。
2. `+ 連絡先を追加` から `individual` 連絡先を選ぶ／新規作成する。
3. 保存。`account_contacts` に紐付け行が作成される。

### 7.4 連絡先（`/contacts`）

#### 7.4.1 作業フロー: 法人連絡先（employee / corporate_rep）

1. `/contacts` → `+ 新規登録` → contact_type「法人代表 / 法人従業員」を選択。
2. 所属法人情報を選択（既存から）。
3. 氏名・役職・メール・電話を入力。
4. 保存。

#### 7.4.2 作業フロー: 個人連絡先（individual）

1. `/contacts` → `+ 新規登録` → contact_type「個人」を選択。
2. 氏名・メール・電話等を入力。
3. 保存後、個人取引先の詳細から「連絡先を追加」で紐付けるか、直接個人取引先を作成時に紐付ける。

### 7.5 タレント（`/talents`）

#### 7.5.1 できること

- 連絡先と 1:1 で紐付く人材特性情報。
- スキル・経歴・ポテンシャル診断（動物占いベース）・星座。

#### 7.5.2 作業フロー: タレント登録

1. `/talents` → `+ 新規登録`。
2. 紐付け先連絡先を選択。
3. 生年月日を入力 → **保存時に自動で以下が算出される**。
   - `potential_number`（1〜60）
   - `constellation`（12 星座）
4. スキル（マスタ `skills` から複数選択）、経歴、メモを入力。
5. 保存。

> ポテンシャル診断は `applyBirthDateDiagnosis` が内部で呼ばれ、マスタ `number_diagnosis` / `constellation_fortune_telling` から結果を引く。マスタ未投入時はエラーになる。

## 8. マスタ・取込（マスタ管理）

`/admin` は **admin ロール専用**。サイドバー「マスタ・取込」から入る。
タブで 19 種のマスタを切り替え、それぞれ作成／編集／論理削除が可能。

### 8.1 タブ構成

| グループ | タブ | 用途 |

| 共通・取引 | パイプライン | `pipeline_types` / `deal_stages` / `deal_statuses` を階層編集 |
|  | 契約種別 | `contract_types` |
|  | サービス | `services` |
| 法人情報 | 法人格 | `corporate_types` |
|  | 法人情報ステータス | `company_statuses` |
| 取引先 | 取引先種別 | `account_types`（法人 / 個人） |
|  | 取引先ステータス | `account_statuses` |
| 連絡先 | 連絡先ステータス | `contact_statuses` |
| リード・マーケティング | リードソース | `lead_sources` |
|  | リードカテゴリ | `lead_categories` |
|  | ステージ・ステータス | `lead_stages` / `lead_statuses`（階層） |
|  | 温度感 | `lead_temperatures` |
|  | コールステータス | `lead_call_statuses` |

| タレント | スキル | `skill_categories` / `skills`（階層） |

### 8.2 作業フロー: マスタ追加

1. `/admin` → 対象タブを選択。
2. 上部の `+ 新規追加` をクリック。
3. フィールド（名前、コード、ソート順、色スワッチ 等）を入力。
4. 保存。一覧に即時反映。

### 8.3 作業フロー: マスタ編集・削除

1. 行の `編集` ボタンから項目を変更して保存。
2. `削除` ボタンは論理削除（`deleted_at` に現在時刻をセット）。参照中のトランザクションデータは残る。
3. 誤削除は `/admin/deleted` から復元可能（admin のみ）。

### 8.4 注意点

- **コードを変更しない**。コード（`code` / `slug`）は Server Action 内で分岐に使われている場合がある。名前変更は可。
- 並び順は `sort_order` を編集。カンバン／プルダウンの表示順に直結。

## 9. 編集・削除の共通ルール

`feedback_edit_flow_unified.md` / `project_delete_policy.md` に基づく全画面共通のルール。

### 9.1 詳細 → 編集 → 保存の統一フロー

- 詳細ページ（`/xxx/[id]`）は**閲覧専用**。インライン編集はしない。
- 右上「編集」ボタン → 編集ページ（`/xxx/[id]/edit`）に遷移。
- 編集ページで「保存」「キャンセル」「削除」を行う。
- 保存後は詳細ページへ戻る。

### 9.2 削除（論理削除）

- 削除ボタンは**編集ページ内**に配置。独立した「危険ゾーン」セクションは置かない。
- クリック時は確認モーダルが表示される（「本当に削除しますか？」）。
- 実行すると `deleted_at` に現在時刻をセット。一覧からは即座に消える。
- 関連する履歴・子レコードは保持される。

### 9.3 復元

- admin のみ `/admin/deleted` にアクセス可能。
- エンティティ別タブから、削除日時・削除者を確認しつつ復元できる。

### 9.4 物理削除について

- **物理削除は提供しない**。DB から行を消す操作は仕様上存在しない（監査証跡確保のため）。
- `deals` は現状 `is_active` 列が未導入のため削除 UI 自体が存在しない。不要な deal はクローズ（失注）で対応。

## 10. アクセス制御と見え方

### 10.1 多層防御

全ての書き込み操作は以下 3 層で保護されている（ユーザーはこれを意識する必要はない）。

1. **Middleware**: 未認証は `/login` へ強制リダイレクト。
2. **Server Action**: 認証チェック + ロールチェック + オーナーチェック。
3. **RLS**: Supabase の Row Level Security で DB レベル制御。

### 10.2 member から見える範囲

- `owner_user_id = 自分` のレコードのみ一覧に表示される。
- 他人の商談 URL を直接叩いても取得できず「見つかりません」表示。
- ダッシュボードの集計も自分持ち分のみ。

### 10.3 manager / admin から見える範囲

- 全件表示。フィルタでメンバー別に絞り込み可能。
- manager は契約の CUD 可。マスタは不可。
- admin はすべて可能。

## 11. よくあるトラブルと対処

| 症状 | 原因 | 対処 |
|---|---|---|
| リード保存時に「Opportunity 昇格には lead_name と account_type_id が必要」エラー | 昇格条件を満たしていない | ステージを Opportunity にする前に、lead_name と account_type_id を埋めて保存する |
| 「このリードはすでに Deal に昇格済みです」 | 二重昇格防止の想定挙動 | 既に生成された Deal を編集する。リード側は参照専用 |
| 商談一覧に削除ボタンがない | 仕様どおり（`is_active` 未導入） | 失注ステージへの遷移で「取り消し」を表現する |
| 他メンバーの商談が見えない | member 権限のため | manager へロール変更を依頼する |
| `/admin` にアクセスしても 404 | admin 以外はメニュー非表示・URL アクセスも拒否 | admin への昇格を依頼する |
| タレント保存時に「ポテンシャル診断マスタが見つかりません」 | `number_diagnosis` / `constellation_fortune_telling` 未投入 | admin に連絡してマスタ投入を依頼 |
| カンバンでドラッグしてもステージが戻る | ネットワークエラーまたは権限不足 | ブラウザのコンソールを確認。それでも解決しない場合は管理者へ連絡 |
| 検索結果が出ない | フィルタが残存している | `フィルタをクリア` ボタンで全解除 |

## 12. リードスコア週次再計算（バッチ運用）

### 12.1 概要

リードのスコア・温度感は、Lead の作成・更新・顧客行動登録のたびにリアルタイム再計算される。
これに加えて、スコアリングルール（マスタ）や企業規模マスタが管理者によって変更された場合、
その変更を全リードに一括反映するために **週次バッチ** が自動実行される。

### 12.2 実行スケジュール

| 項目 | 内容 |
|---|---|
| 実行タイミング | 毎週日曜 03:00（JST） |
| UTC 換算 | 毎週土曜 18:00（UTC） |
| cron 書式 | `0 18 * * 6` |
| pg_cron jobname | `recalculate_lead_scores_weekly` |

### 12.3 処理内容

1. `leads` テーブルの全有効レコード（`deleted_at IS NULL`）をループ
2. 各リードについて企業規模を再判定し、マスタ変更があれば `company_size_id` を更新
3. `recalculate_lead_score` を実行し、スコア・温度感・内訳（breakdowns）を更新

### 12.4 ログ確認

Supabase Dashboard > Database > Logs（NOTICE レベル）で以下のメッセージを確認できる:

```
[recalculate_all_lead_scores] N リードの再計算を完了
```

### 12.5 手動実行（緊急時）

スコアリングルールを変更した直後に即時反映が必要な場合、admin 権限で以下を実行:

```sql
SELECT recalculate_all_lead_scores();
-- 戻り値: 処理した Lead 件数
```

Supabase Dashboard > SQL Editor で実行可能。

### 12.6 注意事項

- 実行中は `statement_timeout` が無効化されるため、Lead 件数が非常に多い場合でも完走する
- マスタ（`lead_score_rules` 等）の変更は翌週バッチで自動反映。緊急の場合は 12.5 の手動実行で対応する
- バッチジョブの登録状況は `SELECT * FROM cron.job WHERE jobname = 'recalculate_lead_scores_weekly';` で確認できる

## 13. バックアップと復旧

Supabase Free プランには PITR（ポイントインタイムリカバリ）が無い。
そのため GitHub Actions で日次の論理バックアップを取得している。

### 13.1 バックアップの仕組み

| 項目 | 内容 |
|---|---|
| ワークフロー | `.github/workflows/db-backup.yml` |
| 実行時刻 | 毎日 JST 03:00（UTC 18:00）。手動実行も可 |
| 形式 | `pg_dump --format=custom`（`pg_restore` で部分復元が可能） |
| 保管先 | GitHub Actions のアーティファクト（保持 30 日） |
| 必要な secret | `SUPABASE_DB_PASSWORD`（DB パスワードのみ。接続文字列ではない） |

取得後に `pg_restore --list` で主要テーブル（leads / deals / contacts / companies / accounts / entity_change_logs）が
含まれることを検証している。空ダンプがそのまま保管されるのを防ぐため。

このジョブは毎日 DB に接続するため、**無操作による Supabase プロジェクトの一時停止も同時に防いでいる**。

### 13.2 復旧手順

1. Actions の該当実行からアーティファクトをダウンロードして展開する
2. 復旧先の接続文字列を用意する（本番へ直接戻す前に、必ず検証用プロジェクトで試すこと）
3. 全体を戻す場合:

```bash
pg_restore --no-owner --no-privileges --clean --if-exists   --dbname "<接続文字列>" iterra-hub-<日時>.dump
```

4. 特定テーブルだけ戻す場合:

```bash
pg_restore --no-owner --no-privileges   --table=leads   --dbname "<接続文字列>" iterra-hub-<日時>.dump
```

### 13.3 運用上の注意

- 保持は 30 日。四半期や年次で残す必要がある場合は、ワークフロー内にコメントしてある R2 退避を有効にする
- 復旧点は最大 24 時間前。それより細かい復旧が必要な業務が出てきた場合は、有償プランの PITR を検討する
- `entity_change_logs`（§ 変更履歴）はトリガーで全変更を記録しているため、
  誤更新の調査は復旧より先にこのテーブルを確認する方が早い
