# タスク管理方針

iterra-hub の作業（依頼・不具合・改善・運用）を取りこぼさないための管理方針。
**個々のタスクの正本は `docs/tasks.md`（台帳）**であり、この文書は運用ルールを定める。

`docs/test-strategy.md`（方針）と `docs/test-checklist.md`（記録）の関係と同じ構成にしている。

最終更新: 2026-08-04

## 1. 背景と原則

- **会話やコミットメッセージはタスクの管理台帳にならない。** セッションをまたぐと
  「依頼したのに手が付いていない」が起きる（2026-08-04、エラー文言の日本語化が
  マスタ管理の 4 箇所にしか入っておらず、他 192 箇所が英語の生エラーのままだった）
- **完了の判定は「実装した」ではなく「本番で使える」**。実装・テスト・本番反映を
  別々に追える形にする（テストのデプロイゲートと同じ考え方）
- 台帳に無いものは着手しない。着手するなら先に起票する（起票は 1 行でよい）
- **タスクを消さない。** 取り下げも履歴として残す。何をやらないと決めたかも情報

## 2. 起票する対象

| 対象 | 例 |
|---|---|
| 利用者からの依頼 | 「エラー文言を日本語にして」「一覧の条件を保持して」 |
| 不具合の報告 | 「取込でタイムアウトする」 |
| ゲートでの検出 | Gate 3 / Gate 4 で見つかった不具合（`test-checklist.md` にも記録） |
| レビュー指摘 | reviewer / designer からの指摘で、その場で直さないもの |
| 運用の残作業 | NAS の鍵認証、実機検証の積み残し |
| 先送りの判断 | 「今回は記録のみ」と決めたもの（**判断も起票する**） |

**起票しないもの**: そのターン内で完結する作業（typo 修正など）。
ただし「後で」と言った瞬間に起票対象になる。

## 3. 台帳の列と意味

`docs/tasks.md` の各行は次を持つ。

| 列 | 意味 |
|---|---|
| ID | `T-0001` 形式の連番。**再利用しない**（取り下げても欠番のまま） |
| 起票日時 | `YYYY-MM-DD HH:MM`（JST）。日付だけでは同日の前後関係が追えない |
| タスク名 | 何を達成すれば終わりかが分かる書き方。「〜を直す」「〜できるようにする」 |
| 種別 | 依頼 / 不具合 / 改善 / 運用 / 調査 |
| 優先度 | 高 / 中 / 低（§4 の基準） |
| 起票元 | 利用者 / Gate 3 / Gate 4 / レビュー / 自主 |
| ステータス | §5 の 6 状態 |
| 実施有無 | **本番で使える状態になったか**を 済 / 未 で持つ（§6） |
| 完了日時 | ステータスが「完了」になった日時 |
| 根拠・記録 | コミット SHA、ドキュメントの節、`test-checklist.md` の該当箇所 |

**ステータスと実施有無を分けるのは、「実装は終わったが本番に出ていない」状態を
見えるようにするため。** 実際にこの取り違えが起きている（2026-08-03 に修正した
migration 8 本が、2026-08-04 まで本番未適用のまま実害を出し続けていた）。

## 4. 優先度の基準

| 優先度 | 基準 |
|---|---|
| 高 | 本番で業務が止まる / データが壊れる / 情報が漏れる。**着手前に他を止める** |
| 中 | 利用者からの依頼、実害はあるが回避できるもの |
| 低 | 改善・整理・将来対応 |

セキュリティに関わるものは実害の有無にかかわらず「高」で起票する。

## 5. ステータス

```
未着手 ──→ 対応中 ──→ 検証中 ──→ 完了
              │           │
              └─→ 保留 ←──┘
              └─→ 取り下げ
```

| ステータス | 意味 |
|---|---|
| 未着手 | 起票しただけ |
| 対応中 | 実装・調査に入っている |
| 検証中 | 実装は終わり、ゲート（テスト）を通している最中 |
| 完了 | §6 の完了条件をすべて満たした |
| 保留 | 判断待ち・前提待ち。**必ず「何を待っているか」を根拠欄に書く** |
| 取り下げ | やらないと決めた。**理由を根拠欄に書く** |

## 6. 完了条件（DoD）

次をすべて満たしたときだけ「完了」にする。ひとつでも欠けるなら「検証中」に留める。

1. 実装が入っている（コミット SHA が特定できる）
2. 対応するテストケース文書を更新した（`docs/test-cases/`）
3. デプロイゲートを通過した（`docs/test-strategy.md` §4）
4. **本番に反映されている**（実施有無 = 済）
5. 設計・仕様を変えたなら、その正本を更新した
   （`database-design.md` / `error-messages.md` / `CLAUDE.md` など）

**「ローカルで動いた」は完了ではない。** 実施有無が「未」のまま完了にしない。

## 7. 運用のタイミング

| タイミング | やること |
|---|---|
| 依頼・報告を受けたとき | **その場で起票する**（着手より先） |
| セッションの開始時 | 台帳の「完了以外」を読み、優先度順に着手先を決める |
| 実装に入るとき | ステータスを「対応中」へ |
| ゲートを通すとき | 「検証中」へ。結果は `test-checklist.md` に記録し、台帳から参照する |
| 本番反映のあと | 実施有無を「済」にし、ステータスを「完了」へ |
| リリースごと | 台帳を棚卸しし、放置されているものを拾う |

## 8. 他の文書との関係

| 文書 | 役割 |
|---|---|
| `docs/tasks.md` | **タスクの正本**（何が残っているか） |
| `docs/task-management.md` | 本書。運用ルール |
| `docs/test-strategy.md` | テストとデプロイゲートの方針 |
| `docs/test-checklist.md` | ゲートの実施記録。タスクの「検証中 → 完了」の根拠になる |
| `docs/deployment-nas.md` | 本番反映の手順。実施有無を「済」にする根拠になる |

**役割を重複させない。** ゲートの結果は `test-checklist.md` に書き、台帳からは参照するだけ。
台帳に検証の詳細を書き写さない。
