## T-0019 の方針メモ（2026-08-04）

**現状**: 数千行の取込を 1 回の HTTP リクエスト内で処理している。設計として選んだ記録はなく、
制限に当たるたびに回避策を足してきた（`lead-import-eight.md` にも「service_role を使う」の
一文しかない）。**DB 側の時間制限を延ばしても、Supabase の HTTP 層のタイムアウトは残る。**

**この環境は非同期化に向いている**:

- アプリは NAS の Docker で**常駐**する。サーバーレスではないのでリクエストを跨いで処理を続けられる
- **pg_cron が既に稼働している**（90 日経過分の物理削除・週次のスコア再計算）

| 案 | 仕組み | 利点 | 欠点 |
|---|---|---|---|
| **A. ジョブテーブル + pg_cron** | 取込内容を `import_jobs` に投入し、pg_cron が拾う。画面は進捗をポーリング | ブラウザを閉じても進む。NAS 再起動にも耐える | 着手まで最大 1 分の遅延 |
| B. アプリ内バックグラウンド | Server Action は登録だけして即返し、常駐 Node が処理 | 遅延なし | コンテナ再起動で中断（ジョブに状態を持てば再開可） |
| C. 分割送信 | クライアントが 200 行ずつ複数回呼ぶ | 実装が最小 | **1 トランザクションでなくなり部分適用が起きる**。CLAUDE.md の「書き込みは DB 関数にまとめる」に反するため採らない |

**推奨は A**（A + B の併用も可。登録時に即起動し、取りこぼしを pg_cron が拾う）。
