# E2E テスト仕様（Playwright）

画面をまたぐ業務ジャーニーの通し走行のみを扱う。画面内の細部（表示・バリデーション・権限の網羅）は
システムテスト（03〜07）の守備範囲であり、E2E では繰り返さない。

最終更新: 2026-08-05

## 1. 実行方式

| 項目 | 値 |
|---|---|
| フレームワーク | `@playwright/test`（TypeScript。§4 のとおり導入する。旧 `scripts/test-*.py` は移行後に廃止） |
| 置き場所 | `e2e/`（シナリオ 1 本 = 1 spec ファイル） |
| ベース URL | `E2E_BASE_URL`（既定 `http://localhost:2000`） |
| ブラウザ | headless Chromium、1440x900 |
| 前提 | `npx supabase start` 済み + `npx supabase db reset` 直後の状態 + `npm run dev` 起動中 |
| 認証 | ロール別に `storageState`（admin / manager / member）を global setup で作成し再利用 |
| データ規約 | 生成データは名称に接頭辞 `E2E-` を付け、シナリオ末尾で論理削除する |
| 実行順序 | ファイル名の昇順。**ログアウトを行うシナリオは最後に置く**（`99-`）。全テストが同じ storageState を使い回すため、途中でログアウトすると以降のテストが未認証になり、開いた画面がログインフォームになる |
| 後片付けの順序 | **リードを先に消す。** リードがステージ要件で商談・契約を参照している間は、それらの削除がトリガーに拒否される（`docs/database-design.md` §24.3）。業務では「ステージを下げてから消す」が正規の手順 |
| 実行コマンド | `npm run test:e2e`（スモークのみ: `npm run test:e2e -- --grep @smoke`） |

## 2. ランク定義

- **S（@smoke）**: デプロイ毎に必須（Gate 3）。基幹業務の生命線
- **A**: リリース前に対象領域へ変更がある場合に実施。nightly 自動実行の対象
- **B**: 月次または大型リリース時

## 3. シナリオ一覧

### E2E-01 [S] ログイン → ダッシュボード → ログアウト

1. 未認証で `/dashboard` へ → `/login` にリダイレクトされる
2. admin でログイン → `/dashboard` 表示、KPI カードとファネルが描画される
3. ログアウト → `/login` へ戻り、`/deals` への直アクセスが再び弾かれる

### E2E-02 [S] リード管理の基本線: 検索 → 詳細 → 社内対応の記録

1. admin で `/leads` を開く（seed 3,008 件・ページネーション 30 件表示）
2. 検索でリードを 1 件特定 → 詳細へ遷移
3. 社内対応（架電記録）を追加 → 一覧に反映・トースト表示
4. スコアが再計算されること（記録前後で値を比較）

### E2E-03 [S] リード → Deal 昇格 → Company / Contact 自動生成

1. admin で昇格対象リードの詳細を開き「商談化」を実行
2. Deal が作成され、Company / Contact が新規作成されて紐づく（Lead 段階の既存紐付けはない仕様）
3. `/deals` カンバンに新規 Deal が現れる。相手先表示は company へフォールバック（account は未作成）
4. 元リードのステージ/ステータスが昇格後の状態になる

### E2E-04 [S] 商談進行 → 契約 → Account 自動作成

1. manager で E2E-03 の Deal をステージ移動（カンバン D&D またはテーブルから変更）
2. stage_updated_at と履歴（deal_stage_histories）が更新される
3. `/contracts/new` で当該 Deal に契約を作成
4. AFTER INSERT トリガーで Account が自動作成され、Deal に紐づく
5. Deal 詳細の相手先表示が account 優先に切り替わる。`/accounts` に新規 Account が現れる

### E2E-05 [S] 権限境界の通し確認（member）

1. member でログイン
2. `/contracts` が閲覧不可（0 件 or 拒否）であること
3. `/admin` への直 URL が拒否されること（middleware）
4. 他人の company 詳細へ直 URL → **閲覧できる**（2026-08-03 変更）。
   参照は認証済み全員に広げたため（`20260803000008`）。
   続けて編集ページで保存すると「編集する権限がありません」で拒否されること
   （**書き込みの範囲は変えていない**ので、権限境界は更新の可否で見る）
5. サイドバーに管理・契約メニューが出ないこと

### E2E-06 [A] Eight 名刺 CSV 取込 → 名寄せ確認

1. admin で `/admin/leads/import` を開き、テスト用 CSV（同じ会社の 2 人 + 取り込めない 1 行）を dry-run
2. 件数が合うこと。**「取込できない行」を数え落とさない**
3. commit → リードが作成される
4. `㈱` 表記の行が `株式会社` に展開されて保存される（元の表記では引けない）
5. **同じ CSV を再度取り込んでも増えない**（2 回目は「新規 0 / 既存に追記 2」）

**Eight の CSV に法人番号の列は無い**ので、当初書いていた「法人番号一致で
既存 Company に名寄せ」はこの経路では確かめられない。名寄せの規則そのものは
DB 関数（`resolve_or_create_company`）と単体テストで見る。

取込は**ジョブ方式**（pg_cron の `process_lead_import_jobs` が 1 分ごと）。
待ち時間が長いので `test.setTimeout` を伸ばしてある。

### E2E-07 [A] 連絡先の作成 → 編集 → 楽観ロック競合

1. admin で individual の連絡先を新規作成（メール・電話チャネル付き）
2. 編集ページを 2 タブで開き、片方で保存 → もう片方の保存が競合エラー（conflictErrorMessage）
3. エラートーストが約 10 秒で自動消滅すること（閉じるボタンでも消せること）

### E2E-08 [A] 論理削除 → 削除済み一覧 → 復元

1. admin が E2E- 接頭辞の company を編集ページ内モーダルから削除
2. 一覧から消え、`/admin/deleted` に表示される
3. 復元 → 一覧に戻る。`entity_change_logs` に削除・復元が記録されている

### E2E-09 [A] マスタ変更の波及: color 編集 → バッジ反映

1. admin が `/admin` に**このテスト専用のステータス**を色付きで作る
   （既存マスタの色を書き換えると実データの見え方が変わるため）
2. そのステータスを付けた事業者情報を作り、一覧のバッジ色が指定どおりであること
3. マスタの色を変えると、一覧のバッジ色も変わること（DB の color をそのまま使う規約の検証）
4. 後片付けは**事業者情報 → マスタ**の順（使用中のマスタは削除できない）

5. 詳細ページのバッジも同じ色であること

一覧はバッジ、詳細は素のテキストという食い違いがあり、**2026-08-05 に
バッジへ揃えた**（T-0056。事業者情報・連絡先・取引先・プロジェクト）。
`InfoField` は `value` に ReactNode を取れるので、器は据え置いて中身だけ差し替えている。

### E2E-10 [B] 定期同期の入口が合言葉なしでは動かないこと

同期エンドポイント 4 本（問い合わせ取込 / Gmail / freee / Google コンタクト）は
**middleware の認証対象から外してある**。認証は各ルートが自前で行うので、
**ここが緩むとログインなしで叩ける口が本番に開く**。

1. 合言葉なしの POST が 401（設定済み）か 503（未設定）を返すこと。**200 にならない**
2. 誤った合言葉でも同じ
3. 返す文言が日本語であること
4. GET では 405 を返すこと

当初は「D1 のテストペイロードを送ってリードが作られること」を書いていたが、
`CLOUDFLARE_*` と合言葉が要るためローカルでは動かせない。
**取り込みそのものの本番確認は T-0036 / T-0055 に残してある。**

### E2E-11 [B] キャンペーン → リード紐付け → 解除

1. admin がキャンペーンを作成し、リードタブからリードを紐付ける
2. 件数表示（`紐付きリード（1 件）`）に出ること
3. **再読み込みしても残っていること。** 紐付けは一覧を楽観更新しているので、
   画面には出たが保存されていない、という壊れ方をここで捕まえる
4. 解除すると 0 件に戻ること（解除は確認ダイアログを挟まない。
   消えるのは紐付けだけでリードは残るため）

### E2E-12 [S] リードステージ要件（商談・契約が伴わない遷移を拒む）

規則の設計は `docs/database-design.md` §24、ケースは 06 の LD-23 / LD-24 / LD-26。
DB トリガー自体の検証は 02 の IT-LEADSTAGE-01（SQL）で行い、ここは
**画面から操作したときに規則が効き、理由が読める文言で出ること**を守る。

1. `/leads/new` のステージ選択肢に Sales / Opportunity / 取引先 が出ない
2. 商談が無いリードを「取引先」へ変更 → 「商談が必要です」で拒否され、ステージは変わらない
3. 「Sales」へ変更 → 昇格ダイアログを経て商談が作られ、**ステータス（商談化）が消えない**
4. 商談はあるが契約が無い状態で「取引先」へ変更 → 「契約が必要です」で拒否

### E2E-13 [S] 新規作成の項目の揃いと、親から子を追加する導線

仕様は 04 の CON-30 / 03 の COM-30。2026-08-04 の指摘に対する回帰テスト。

1. 事業者情報の詳細に「連絡先を追加」があり、`?company_id=` 付きで作成画面へ移る
2. 連絡先の新規作成に**連絡手段・住所の欄がある**（旧実装には無かった）
3. メール・電話・住所を入れて作成すると、**作成と同時に子テーブルまで入る**
4. 連絡先の詳細から「商談を追加」で、相手先が**連絡先で初期選択**された商談作成画面へ移る
   （取引先が無くても商談を作れること）

### E2E-14 [S] 日本語入力（IME）の変換中に検索が走らない

2026-08-05 の指摘に対する回帰テスト。**同じ不具合を何度も出している。**

変換中は未確定の文字が入力欄の value に入る。それで検索すると結果の再描画が
変換中の入力を壊し、「打った文字が消える・確定できない」が起きる。

1. 一覧の検索欄（`/companies`）で「かいしゃ」を**変換中の状態**にする
   → 表示は追従するが、待ち時間（300ms）を過ぎても `?search=` が付かない
2. 「会社」で確定する → `?search=会社` になり結果が絞り込まれる
3. 横断検索（Ctrl+K）でも変換中は候補を出さない
4. 検索付きの選択欄で、**変換を確定させた Enter が候補を確定させない**
5. 住所の「市区町村」を変換中にして Enter で確定する
   → **フォームが送信されず**、打った文字も URL も変わらない
6. 「郵便番号」を変換中にして Enter で確定する
   → **住所検索が走らない**（走ると、かなを郵便番号として引きに行って失敗する）

**キー入力の模倣では再現できない**（composition イベントが出ない）。
CDP の `Input.imeSetComposition` で本物の変換を起こすこと。

5 と 6 は 2026-08-05 に追加した。E2E-13 は素の Enter しか見ておらず、
**変換確定の Enter は誰も見ていなかった**（利用者が繰り返し指摘していたのはこちら）。
確認した結果 `AddressesEditor` の実装は正しく、**直す必要は無かった**。

なお `AddressesEditor` の判定は `e.nativeEvent.isComposing` だけを見ており、
`useSearchField` のように変換中の印を自前で持ってはいない。Chromium では
変換を確定させた Enter の keydown が `isComposing = true` になるため成立する。
**別のブラウザを対象に加えるときはここを見直すこと。**

判断そのものの単体テストは `src/lib/search-field.test.ts`（UT-66）。
**検索欄を足したらここに 1 行足す。**

### E2E-15 [A] 兼務（1 人が複数の事業者情報に関わる）

`contacts.company_id` は「主たる所属」で 1 社しか持てない。2 社目以降は
`company_contacts` に入れる（2026-08-06。T-0059）。freee の突合で、
同じ人が 2 社の担当者になっている例が出たのが発端。

1. 主たる所属を持つ連絡先を作る → 兼務先は 0 件
2. 2 社目を兼務として足す（役職も入れられる）
3. **兼務先の事業者情報の連絡先一覧に「兼務」バッジ付きで出る**
   （主たる所属だけを見ていると取りこぼす、というのがこの機能の要点）
4. 主たる所属の側にも今までどおり出る
5. **主たる所属と同じ事業者は候補に出ない**（DB のトリガーも拒むが、
   押せてからエラーになるより出さない方がよい）
6. 外すと 0 件に戻る。連絡先そのものは残る

### E2E-16 [A] 連携プロファイル（事業者情報 × 連携先）

freee へ渡す担当者メールは「主担当の主メール」で決まる。**主メールは連絡先に
1 つしか立たない**ため、同じ人が 2 社の主担当だと両社へ同じメールが渡る
（2026-08-06。T-0060）。

1. メールを 2 つ持つ連絡先を作り、事業者 A の所属・B の兼務にする
2. A・B 両方の主担当にする
3. **既定ではどちらも同じ（主）メールが渡る**（これが直したい状態）
4. B のプロファイルで 2 つ目のメールを選ぶ → B に渡る値が変わる
5. **A は影響を受けない**（同じ連絡先だが主メールのまま）
6. 「既定に従う」へ戻せる
7. **担当者を選び直すとメールの選択が外れる**（前の人のメールを持ったまま
   保存すると DB のトリガーに弾かれるため、押せる前に外す）

**差分画面（`/admin/freee/sync`）からの操作は E2E に入れていない。**
freee の接続と取引先データが要り、ローカルでは作れないため。
代わりに psql で `ignored_fields` が差分から項目を落とすことを確認している
（4 項目 → 対象外 1 つ → 3 項目 → 戻して 4 項目）。

### E2E-17 [A] 商談の相手先を複数紐づける / 契約を商談へ紐づける

商談の相手は「Ａ社のＢさん」であることが普通だが、2026-08-07 まで画面が
ラジオで 1 つしか選ばせておらず、DB 制約（いずれか 1 つ以上）より狭かった（T-0064）。
併せて、商談フォームの「契約名」が `contracts` と二重管理になっていたのを
契約テーブルへ一本化した（T-0063）。

1. 新規作成に**契約名の入力欄が無い**こと・「契約は商談を作成したあとに」の案内が出ること
2. 事業者情報と連絡先を**両方**選べること（片方を選んでもう片方が外れない）
3. 詳細で**両方リンクが出る**こと（1 件だけ返す実装だと連絡先が事業者情報の陰に隠れる）
4. 別の商談に契約を作り、編集画面の「既存の契約を紐づける」で付け替えられること
5. 候補一覧に**移動元の商談**が出ること（紐づけると元から外れるため）
6. 付け替え後、移動先に出て**移動元からは消える**こと

**後片付けの順序に注意。** 契約が残ると商談を消せず、**取引先が残ると事業者情報を消せない**。
取引先は契約作成の AFTER INSERT トリガーが作ったもので、契約を消しても残る。

### 総ざらい（`@sweep`）— 画面を変えたら必ず回す

**「自分が書いたテストが通る」ことと「画面が使える」ことは別。** 2026-08-04 に
住所が Enter で消える・個人事業主に法人向けの項目が出るといった不具合を
利用者に指摘されたが、いずれも**画面を一度開けば気づけた**もので、
既存の E2E が全部緑だったため見落としていた。

`e2e/zz-sweep.e2e.ts` が主要画面を一通り開いて操作する。

| 見るもの | 中身 |
|---|---|
| 開くこと | 主要な一覧・新規作成が 200 で返り、JS エラーが出ない |
| 出し分け | 個人事業主に法人向けの項目（法人番号・代表者・登記事項証明書）が出ない |
| 画面を跨ぐ約束 | 商談の相手先が 3 択、連絡先の新規作成に連絡手段と住所がある など |

```bash
npm run test:sweep     # 総ざらい（30 秒ほど）
npm run test:e2e       # スモーク 7 本（@sweep は除く）
```

**既定の `test:e2e` からは外してある。** 一緒に走らせると重くて共倒れする
（実際に 240 秒のタイムアウトに当たった）。

**画面を変えたら、この一覧に足すこと。** 説明文のような細かい表示も、
`innerText` に禁止語が出ないかで機械的に拾える
（実際、条件分岐を入れたつもりが説明文に「法人番号」が残っていたのを 2 箇所検出した）。

## 4. 導入手順（Phase 1）

```bash
npm install -D @playwright/test
npx playwright install chromium
```

- `playwright.config.ts`: baseURL 環境変数、global setup で 3 ロールの storageState 生成
- `package.json` に `"test:e2e": "playwright test"` を追加
- CI への組み込みは test-strategy.md §7 Phase 3（supabase start が必要なため nightly）

## 5. 実装優先順位

1. E2E-01, 05（認証・権限。最小コストで多層防御を毎回確認できる）
2. E2E-03, 04（Lead → Deal → 契約 → Account はこのシステムの生命線かつ手動確認が最も面倒）
3. E2E-02, 06（日次業務と取込）
4. 残り

### 6.0 一覧の条件反映と遷移の競合（2026-08-04）

**症状**: 一覧の検索欄に語を入れた直後に結果の行を押すと、詳細ページへ遷移しない。
E2E-02 / 03 / 04 が同時に赤くなって判明した（3 本とも「作成 → 一覧で検索 → 行を押す」の手順）。
**特定の一覧の問題ではない。** `useListView` を使う全一覧が同じ経路を持つ
（リード一覧を直した後、E2E-04 が今度は契約一覧の同じ箇所で赤くなった）。

**機序**: 検索語は `SearchInput` の debounce（300ms）を経て `useListView` → `useListParams` で
`router.replace()` により URL のクエリへ載る。押した直後にこの replace が走ると、
クリックで始まった `push` が差し替えられて遷移が消える。**§6.1 と同じ機序**で、
一覧の条件を URL に置く変更（2026-08-04）で新しく成立するようになった経路。

**テスト側の対応**: `searchInList()`（`e2e/helpers.ts`）で、検索語が URL に載るまで待ってから
行を押す。待たずに押していた従来のコードは、絞り込み前に並んでいた行を押しており、
「検索で 1 件に特定してから選ぶ」という仕様の手順自体を通っていなかった。
**テストを緩めたのではなく、手順に忠実にした修正**である。

**実装側に残る論点**: 打鍵から 300ms 以内に行を押すと利用者にも同じことが起きる。
実操作でこの速さは出にくいため今回のリリースでは修正していない。直すなら
`router.replace()` を `window.history.replaceState` に替えて RSC の再取得を伴わない
URL 更新にする案が第一候補（進行中のナビゲーションを打ち消さなくなる）。

**同じ待ちで見つかった実装の不具合（2026-08-04 修正済み）**:
テストが検索の反映を待つようになったことで、**表示モードの切り替え直後に検索すると
`view=table` が URL から落ち、一覧がカンバン表示に戻る**ことが分かった（E2E-03）。

`useListParams` の `apply()` がレンダー時点の条件を基に URL を組み直していたのが原因。
`router.replace` は**サーバーコンポーネントの取り直しが終わってから履歴を書き換える**ため、
続けて操作すると直前の変更が `searchParams` にも `window.location` にも現れていない。
検索欄は debounce（300ms）で入力時点のコールバックを後から実行するため特に踏みやすい。

**検索に限らず、条件を続けて変える操作すべてが対象だった**（ステージを選んだ直後に
ステータスを選ぶ、並び替えた直後にページを送る、など）。

修正は `apply()` が未反映の条件を ref に持ち、次の変更をそこへ重ねる形
（URL に現れたら ref を捨てて URL を正に戻す）。**`window.location.search` を
読み直す案では直らない。** 履歴の書き換え自体が遅れているため、そこにも
まだ現れていない。

### 6.0.1 dev サーバーと `next build` を同時に走らせない（2026-08-04）

**症状**: global setup のログインが `waitForURL("**/dashboard")` でタイムアウトし、
E2E が 1 本も走らない。手で操作してもログインボタンが反応せず、
Supabase の auth へのリクエストが飛ばない（コンソールにもエラーが出ない）。

**原因**: dev サーバーを起動したまま `npm run build` を回すと、両者が同じ `.next` を
使うため dev 側の状態が壊れる。**アプリの不具合ではない。**
認証エンドポイント自体は生きている（`/auth/v1/token` に直接 POST すると
access_token が返る）ので、そこを叩いて切り分けられる。

**対処**: dev サーバーを止め、`.next` を消してから起動し直す。
Gate 1（build を含む）と E2E を続けて回すときは、**build のあとに dev を再起動する**。

### 6.1 保存後の自動遷移（2026-08-03 修正済み）

- ~~**`router.push(id); router.refresh();` の直後連続呼び出しでクライアント遷移が固まることがある**~~

  報告されるまで検知できなかった。** E2E 側が「その操作自身の自動遷移を待たない」回避を

  **テストを実装の都合に合わせて緩めると、その分だけ検知できなくなる。**

### 6.2 スコアリングのシード不具合（2026-08-03 修正済み）

**症状**: 架電結果を記録してもリードスコアが動かない。E2E-02 がこれを検出した。

**原因**: `supabase/seeds/01-masters.sql` の `lead_score_rules`（M26）が、
`condition_value_id` を決めるサブクエリで参照する `lead_large_segments`（M14）と
`lead_call_statuses`（M16）より **前** に置かれていた。seed は上から順に流れる 1 本の SQL なので、
INSERT 時点でこれらのテーブルは空で、サブクエリが NULL を返していた。
`recalculate_lead_score()` は `condition_value_id IS NULL` の行を評価対象外にするため、
エラーも警告も出ないまま以下 5 ルールが一生マッチしない状態だった:

- call_status: 資料送付済み(+10) / 見込み判定(+25) / アポ獲得(+40)
- large_segment: 製造業(+10) / IT・SaaS(+10)

**本番にも同じ欠落があったはず**（同じ seed を使うため）。

**対応**:

1. seed の M26 ブロックを全マスタの後ろへ移動し、順序依存であることをコメントで明記した
2. 既存環境（本番含む）は seed 再実行では直らないため、
   `20260803000004_backfill_lead_score_rule_targets.sql` で NULL 行を description から
   引き当てて補正し、`recalculate_all_lead_scores()` で全リードのスコアを揃えた

**検証済み**: 育成ステージのリード（score 10）に「アポ」の架電記録を足すと 50 になる
（修正前は 10 のまま）。db reset 後も NULL 0 件。
